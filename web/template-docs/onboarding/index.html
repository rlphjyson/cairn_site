Onboarding template

A mobile onboarding flow built only from cairn_ui: splash, value pages, permissions, personalisation, an account choice and a calm summary. This guide takes you from copy it in to shipping it with your own content, storage and permissions.

Overview

The template is a Flutter package, cairn_template_onboarding, that exposes one widget, OnboardingApp, and a handful of types your app implements or receives. It runs six screens:

  • Splash – the brand mark fades in once and the flow moves on as soon as its content has loaded.
  • Value pages – four swipeable pages with a large photograph, a title and a line of body text; dots, Skip, Next / Get started, and back by swipe or gesture.
  • Permissions – a card each for notifications and location (camera is one JSON entry away), with benefit copy and an Allow button that calls your PermissionService.
  • Personalise – interests (at least three), one goal and a reminder time, one part per screen, with CairnSteps showing where you are. It cannot be skipped.
  • Account – Create account, I already have an account, Continue as guest. No forms: the choice is handed to your app.
  • Done – a summary and a Start button that calls onCompleted(OnboardingResult).

Progress is saved after every change, so closing the app and re-opening it continues where the user left off. It is organised as clean architecture by layer, then by feature, with flutter_bloc for state and get_it for dependency injection. Nothing is generated.

lib/ ├─ onboarding_app.dart entry widget (OnboardingApp) ├─ core/ │ ├─ infrastructure/ get_it registration (di/), the host's callbacks │ └─ presentation/ navigation cubit, ViewModel, step layout, motion ├─ common/ brand, layout, personalise parts, helpers ├─ data/<feature>/ content source, progress store, permission demo ├─ domain/<feature>/ models, mappers, repository interfaces, use cases └─ presentation/<feature>/ bloc, view models, views, widgets (+ shell/)
The one rule to remember

Dependencies point inwards: presentation → domain ← data. To change what the onboarding says you touch one JSON map. To change where it stores things or how it asks the platform you pass an object to OnboardingApp. You never fork the template to integrate it.

Requirements

ToolVersion

The template has no platform code and no plugins of its own. Storage and permissions are interfaces you implement, so adding or swapping a plugin never touches the template.

Install

A. As a package (recommended)

Keeping it a package means you can pull in fixes later with a version bump.

# pubspec.yaml
dependencies:
  cairn_ui: ^0.2.0
  cairn_template_onboarding:
    git:
      url: https://github.com/rlphjyson/cairn_site.git
      path: templates/onboarding
      ref: main            # pin a tag or commit for production
  shared_preferences: ^2.3.0

Or, from a local checkout: path: ../cairn_site/templates/onboarding. The four photographs ship inside the package and are found automatically (OnboardingPackage.name).

B. Copy the source into your app

  1. Copy templates/onboarding/lib/ into lib/onboarding/ and templates/onboarding/assets/images/ into your app's assets/onboarding/ (any folder you like).
  2. Add cairn_ui, flutter_bloc, get_it and equatable to your pubspec.yaml, and declare the image folder under flutter: assets:.
  3. In lib/common/constants/onboarding_package.dart set static const String? name = null; so images resolve from your app instead of the package, and update the image paths in the content to match your folder.
  4. Rewrite the package:cairn_template_onboarding/… imports to your app's package name (a find-and-replace). Files inside the template use relative imports, so only your own references change. Delete cairn_template_onboarding.dart if you do not want the barrel.
Photographs

The images are from Pexels under the Pexels licence (see NOTICE.md). They are placeholders for the demo: replace them with your own artwork before you ship, and keep each to roughly 150 KB so the first page does not wait on a decode.

Mount it

The template reads colours, radii and type from CairnTheme, so the host app must provide one. Below is a complete main.dart with a "show once" gate: the first launch shows onboarding, every later launch goes straight to the app. Progress survives the app being killed mid-way.

import 'dart:convert';

import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';
import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';

/// Keeps onboarding progress as one JSON string in shared_preferences.
class SharedPreferencesProgressStore implements ProgressStore {
  SharedPreferencesProgressStore(this._prefs);

  static const String _key = 'onboarding.progress';

  final SharedPreferences _prefs;

  @override
  Future<Map<String, Object?>?> read() async {
    final String? raw = _prefs.getString(_key);
    if (raw == null) return null;
    try {
      return Map<String, Object?>.from(jsonDecode(raw) as Map<Object?, Object?>);
    } on Object {
      return null; // unreadable: the flow starts over instead of crashing
    }
  }

  @override
  Future<void> write(Map<String, Object?> json) =>
      _prefs.setString(_key, jsonEncode(json));

  @override
  Future<void> clear() => _prefs.remove(_key);
}

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final SharedPreferences prefs = await SharedPreferences.getInstance();
  runApp(MyApp(prefs: prefs));
}

class MyApp extends StatefulWidget {
  const MyApp({super.key, required this.prefs});

  final SharedPreferences prefs;

  @override
  State<MyApp> createState() => _MyAppState();
}

class _MyAppState extends State<MyApp> {
  static const String _seenKey = 'onboarding.seen';

  late bool _seen = widget.prefs.getBool(_seenKey) ?? false;

  Future<void> _finish(OnboardingResult result) async {
    await widget.prefs.setBool(_seenKey, true);
    // Keep what the user told you: your own storage or API goes here.
    await widget.prefs.setStringList('interests', result.interests);
    if (!mounted) return;
    setState(() => _seen = true);
    // result.accountChoice says where to go next: see "Hand off to auth".
  }

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Daybreak',
      theme: CairnTheme.materialTheme(CairnTheme.light),
      darkTheme: CairnTheme.materialTheme(CairnTheme.dark),
      home: _seen
          ? const HomeScreen()
          : Scaffold(
              body: SafeArea(
                child: OnboardingApp(
                  progressStore: SharedPreferencesProgressStore(widget.prefs),
                  onCompleted: _finish,
                ),
              ),
            ),
    );
  }
}

class HomeScreen extends StatelessWidget {
  const HomeScreen({super.key});

  @override
  Widget build(BuildContext context) =>
      const Scaffold(body: Center(child: Text('Welcome back')));
}

OnboardingApp fills whatever space its parent gives it (320 × 640 and up), so put it in a Scaffold body, a CairnMockupPhone or a fixed-height box. From 600 px wide it stays a centred 440 px column. Each instance creates its own dependency container and disposes it, so two copies never share state. Wrap it in a SafeArea as above, since the template draws its own progress bar and footer edge to edge.

Why a separate "seen" flag?

The saved progress also records completed, so you could read it back. A one-line boolean of your own is simpler to reason about, survives a change of the saved format, and is the thing you will want to reset when a user signs out on a shared device.

Arguments

ArgumentTypeMeaning
onCompletedvoid Function(OnboardingResult)?The user pressed Start. Called once.
onSkippedvoid Function(OnboardingStepKind)?The user skipped a step that allows it. Informational: the flow moves on by itself.
onStepChangedvoid Function(OnboardingStepKind)?A step was shown, including the first. For analytics.
flowDataSourceFlowRemoteDataSource?Where the content comes from. Default: InMemoryFlowRemoteDataSource.
progressStoreProgressStore?Where progress is kept. Default: InMemoryProgressStore, which forgets everything when the app closes.
permissionServicePermissionService?How permissions are requested. Default: DemoPermissionService, which grants everything without a system prompt.
startAtStepOnboardingStepKind?Open on this step and skip the splash. Read once, when the app is first built.
showReplayboolOffer "Replay from the start" on the last step. For demos; leave it off.

The callbacks may change between builds (a setState in the parent is fine); the flow is not restarted. The three objects are read once, when the widget is first built.

The result

FieldMeaning
interestsChosen interest ids, in the order the content lists them.
goalIdThe chosen goal id (null if the content has no personalise step).
reminderIdThe chosen reminder option id.
permissionsMap<PermissionKind, PermissionStatus>: the answer to every permission that was asked for. Ones never asked are absent.
accountChoiceAccountChoice.createAccount, signIn or guest. guest when the user skipped the step or the content has none.

The flow

splash ──► welcome ───────► permissions ──► personalise ──────────────► account ──► done (fade, 4 pages 2 cards interests ► goal ► reminders 3 choices summary load) Skip ──────────► Skip ────────► (cannot be skipped) Skip=guest Start ▲ ▲ ▲ │ │ └── back ──────────┴─────── back ───┘◄─────── back ────────────┘ ▼ onCompleted(result)

The steps and their order are content: the steps list in the flow JSON. The default is welcome, permissions, personalise, account, done. Leave one out and it is simply not shown; done is always last.

Rules

  • Skip is offered on the welcome pages, the permissions and the account step. It moves to the next step and calls onSkipped. Skipping the account step means AccountChoice.guest. Skipping the permissions asks for nothing.
  • Personalise cannot be skipped, whatever the JSON says, and the flow will not move past it until there are at least minInterests valid interests, a goal and a reminder choice (CanAdvance). CompleteOnboarding checks the same rule again, so a restored or hand-edited state can never reach the host half-answered.
  • Back steps through the pages and the personalise parts before it leaves a step. The system back gesture does the same; on the very first page it is left to your app.
  • Resuming restores the step, the page, the personalise part and every answer. Content that has changed since is repaired: a removed step falls back to the first; a page index past the end is clamped; interests, goals, reminders and permissions the content no longer offers are dropped.
  • Saving never blocks. If the store throws, the user carries on; they simply cannot resume.

Change the content

Everything the flow says comes from one place: lib/data/flow/remote/flow_remote_data_source.dart. Today it is an in-memory stand-in that returns decoded JSON, exactly what an HTTP client or a remote-config SDK would hand you. That makes it the one place to edit, and the one place to replace (see Remote-config content).

JSON shapes

The mapper in domain/flow/mappers/flow_mapper.dart reads these keys. Anything not listed is ignored.

KeyFields
steps[]kind (welcome | permissions | personalise | account | done), optional title, body (the step's heading and line), optional skippable (default true)
pages[]id, title, body, image (asset path), optional imageLabel (what the photograph shows, read by screen readers)
permissions[]kind (notifications | location | camera), title, benefit, optional deniedHelp (how to enable it later), optional optional
personaliseminInterests (default 3), defaultReminder (a reminder id), interests[] (id, label), goals[] (id, label, hint), reminders[] (id, label)
Forgiving about structure, strict about types

Unknown or repeated step kinds are ignored; a welcome step with no pages or a permissions step with no cards is dropped. A wrong type (a number where a string belongs) or a missing required key makes loading fail, and the splash screen shows a retry. Ids are saved with the user's progress, so keep them stable when you reword a label.

Pages and images

Edit a page in place, or add one. Add the image to assets/images/ (it is already declared in pubspec.yaml as a folder), then:

Interests, goals and reminders

Inside the personalise object. Interests are chips that wrap, so ten to fourteen short labels read well; goals are cards with a hint; reminders fill the select. To require more interests set minInterests; the message ("Pick 2 more to continue.") follows. defaultReminder must be one of the reminder ids, or omitted to make the user choose.

The headings of the three personalise parts and the sample reminder notification are not content but constants: common/constants/personalise_sections.dart and common/constants/onboarding_brand.dart. The splash name and tagline are in the same brand file.

Add or remove a step

Remove one

Delete its entry from steps (or from your remote JSON). Nothing else changes: navigation, the progress bar ("step 2 of 4"), the summary rows and the result all follow the list. Removing permissions leaves OnboardingResult.permissions empty; removing account makes accountChoice always guest; removing personalise removes the rules that guard it.

Reorder

Reorder the entries. Putting account before personalise, for example, just works; the done step stays last.

Add a new kind of step

Say an "Invite a friend" screen. The compiler guides you: the shell switches exhaustively on OnboardingStepKind, so a missing case is an error, not a blank page.

  1. Add invite to the OnboardingStepKind enum in domain/flow/models/onboarding_step.dart. The mapper accepts it automatically.
  2. Create presentation/invite/views/invite_view.dart (below).
  3. Add OnboardingStepKind.invite => const InviteView(), to the switch in presentation/shell/onboarding_shell.dart.
  4. Add {'kind': 'invite', 'title': 'Better together', 'body': 'Invite a friend.', 'skippable': true} to steps, before done.
import 'dart:async';

import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/widgets.dart';
import 'package:flutter_bloc/flutter_bloc.dart';

import '../../../core/presentation/widgets/footer_button.dart';
import '../../../core/presentation/widgets/step_layout.dart';
import '../../../domain/flow/models/onboarding_step.dart';
import '../../flow/bloc/onboarding_cubit.dart';

class InviteView extends StatelessWidget {
  const InviteView({super.key});

  @override

    final OnboardingCubit cubit = context.read<OnboardingCubit>();
    final OnboardingState state = cubit.state;

    return StepLayout(

The top bar's Skip button appears automatically when the step's skippable is true. If the new step collects data that must be saved, add a field to OnboardingProgress and its mapper (domain/progress/mappers/progress_mapper.dart) and bump ProgressMapper.version so older saved data is ignored rather than misread. If it must be validated, add the rule to CanAdvance; it is pure and unit-testable.

Real permissions

The template never talks to the operating system. Its PermissionService is three methods, and the default DemoPermissionService grants everything without a prompt so the flow works on web, desktop and in tests. For a real app implement the interface with permission_handler:

import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';
import 'package:permission_handler/permission_handler.dart' as ph;

class PermissionHandlerService implements PermissionService {
  const PermissionHandlerService();

  ph.Permission _permission(PermissionKind kind) => switch (kind) {
    PermissionKind.notifications => ph.Permission.notification,
    PermissionKind.location => ph.Permission.locationWhenInUse,
    PermissionKind.camera => ph.Permission.camera,
  };

  PermissionStatus _status(ph.PermissionStatus status) => switch (status) {
    ph.PermissionStatus.granted ||
    ph.PermissionStatus.limited ||
    ph.PermissionStatus.provisional => PermissionStatus.granted,
    ph.PermissionStatus.denied => PermissionStatus.denied,
    // The system will not show its prompt again: the only way back is Settings.
    ph.PermissionStatus.permanentlyDenied ||
    ph.PermissionStatus.restricted => PermissionStatus.permanentlyDenied,
  };

  @override
  Future<PermissionStatus> status(PermissionKind kind) async =>
      _status(await _permission(kind).status);

  @override
  Future<PermissionStatus> request(PermissionKind kind) async =>
      _status(await _permission(kind).request());

  @override
  Future<void> openSettings() async {
    await ph.openAppSettings();
  }
}

// Then:
OnboardingApp(
  permissionService: const PermissionHandlerService(),
  onCompleted: _finish,
)

Platform setup

  • Android – declare the permissions in android/app/src/main/AndroidManifest.xml: POST_NOTIFICATIONS (Android 13+), ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION, CAMERA.
  • iOS – add the usage strings to Info.plist (NSLocationWhenInUseUsageDescription, NSCameraUsageDescription) and enable each permission's macro in the Podfile (PERMISSION_NOTIFICATIONS=1, PERMISSION_LOCATION=1, PERMISSION_CAMERA=1 under GCC_PREPROCESSOR_DEFINITIONS). Unlisted permissions are compiled out and always report denied.

Check permission_handler's own README for the current keys; they change with the plugin, not with this template.

What the template does with the answer

  • granted: the card shows an "Allowed" badge.
  • denied: the card explains (the content's deniedHelp) how to enable it later, and offers Try again and Open settings.
  • permanentlyDenied: only Open settings, because a retry would do nothing.
  • An exception from your service, or notDetermined after asking, is treated as denied, so a missing plugin can never trap the user.
Add the camera

Add {'kind': 'camera', 'title': 'Camera', 'benefit': 'Scan a receipt or add a photo to a habit.'} to permissions. A third card appears; nothing else changes.

A good onboarding asks in context, with the benefit visible, and lets people decline. The template's cards are built that way: each says why, nothing is requested until the button is pressed, and Continue is always available.

Remote-config content

Implement FlowRemoteDataSource and return the JSON from anywhere. FlowRepositoryImpl caches the mapped flow for the life of the app instance; the splash screen waits for it, so keep the call fast and always fall back to the built-in content.

Firebase Remote Config

import 'dart:convert';

import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';
import 'package:firebase_remote_config/firebase_remote_config.dart';

class RemoteConfigFlowDataSource implements FlowRemoteDataSource {
  RemoteConfigFlowDataSource(
    this._config, {
    this.fallback = const InMemoryFlowRemoteDataSource(),
  });

  final FirebaseRemoteConfig _config;
  final FlowRemoteDataSource fallback;

  @override
  Future<Map<String, Object?>> fetchFlow() async {
    try {
      await _config.fetchAndActivate().timeout(const Duration(seconds: 3));
      final String raw = _config.getString('onboarding_flow');
      if (raw.isEmpty) return fallback.fetchFlow();
      return Map<String, Object?>.from(jsonDecode(raw) as Map<Object?, Object?>);
    } on Object {
      return fallback.fetchFlow(); // offline, timed out or malformed
    }
  }
}

Your own REST endpoint

import 'dart:convert';

import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';
import 'package:http/http.dart' as http;

class HttpFlowDataSource implements FlowRemoteDataSource {
  HttpFlowDataSource(this._client, {required this.url, this.locale});

  final http.Client _client;
  final Uri url;
  final String? locale;

  @override
  Future<Map<String, Object?>> fetchFlow() async {
    final http.Response res = await _client.get(
      url,
      headers: <String, String>{if (locale != null) 'Accept-Language': locale!},
    );
    if (res.statusCode != 200) {
      throw http.ClientException('Onboarding content failed: ${res.statusCode}');
    }
    return Map<String, Object?>.from(jsonDecode(res.body) as Map<Object?, Object?>);
  }
}

// Then:
OnboardingApp(flowDataSource: HttpFlowDataSource(client, url: Uri.parse('https://api.example.com/onboarding')))

If the call throws, the splash screen shows "We could not load the welcome" with a Try again button. If you would rather never block the user, catch the error and return the in-memory content as above. To use network images for the pages, see Pages and images.

Test the JSON before you publish it

Run the same map through FlowMapper.fromJson in a unit test (the template's test/domain_test.dart does this for the built-in content). A typo that fails there would fail on every user's phone.

Persist progress

ProgressStore is three methods over a small JSON object, so anything fits. The shared_preferences implementation is in Mount it. A file-based one is as short:

import 'dart:convert';
import 'dart:io';

import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';

class FileProgressStore implements ProgressStore {
  FileProgressStore(this._file);

  final File _file;

  @override
  Future<Map<String, Object?>?> read() async {
    if (!_file.existsSync()) return null;
    try {
      return Map<String, Object?>.from(
        jsonDecode(await _file.readAsString()) as Map<Object?, Object?>,
      );
    } on Object {
      return null;
    }
  }

  @override
  Future<void> write(Map<String, Object?> json) =>
      _file.writeAsString(jsonEncode(json));

  @override
  Future<void> clear() async {
    if (_file.existsSync()) await _file.delete();
  }
}
  • What is saved: version, step, pageIndex, section, permissions, interests, goalId, reminderId, accountChoice and completed. It is written after every change, not only at the end. None of it is secret.
  • Versioning: ProgressMapper.version is bumped when the shape changes incompatibly. Data from another version is ignored and the flow starts over; it is never half-read.
  • Per user: if several people share a device, include the user id in your store's key, and call clear() (or remove the key) on sign-out.
  • Replay: OnboardingApp(showReplay: true) adds a "Replay from the start" link to the last step, which clears the store and returns to the first page. It is meant for demos.
  • Never blocks: a store that throws on write is ignored; one that throws on read means a fresh start.

Analytics hooks

Three callbacks cover the funnel; a decorator covers permissions, which the template does not otherwise report.

OnboardingApp(
  onStepChanged: (OnboardingStepKind step) =>
      analytics.log('onboarding_step', <String, Object?>{'step': step.name}),
  onSkipped: (OnboardingStepKind step) =>
      analytics.log('onboarding_skip', <String, Object?>{'step': step.name}),
  onCompleted: (OnboardingResult result) =>
      analytics.log('onboarding_done', <String, Object?>{
        'interests': result.interests.length,
        'goal': result.goalId,
        'reminder': result.reminderId,
        'account': result.accountChoice.name,
        'granted': <String>[
          for (final e in result.permissions.entries)
            if (e.value.isGranted) e.key.name,
        ],
      }),
  permissionService: AnalyticsPermissionService(
    inner: const PermissionHandlerService(),
    log: analytics.log,
  ),
)

/// Reports every answer, then returns it unchanged.
class AnalyticsPermissionService implements PermissionService {
  AnalyticsPermissionService({required this.inner, required this.log});

  final PermissionService inner;
  final void Function(String event, Map<String, Object?> data) log;

  @override
  Future<PermissionStatus> status(PermissionKind kind) => inner.status(kind);

  @override
  Future<PermissionStatus> request(PermissionKind kind) async {
    final PermissionStatus result = await inner.request(kind);
    log('permission_result', <String, Object?>{
      'kind': kind.name,
      'status': result.name,
    });
    return result;
  }

  @override
  Future<void> openSettings() => inner.openSettings();
}

onStepChanged fires for the first step too (and for every step re-shown after a back), so count distinct steps if you build a funnel. PermissionStatus.isGranted is exported with the barrel's PermissionStatus.

Hand off to auth

The account step builds no forms. It records one of three choices and, when the user presses Start, OnboardingResult.accountChoice arrives in onCompleted. Route on it. The authentication template (templates/auth, package cairn_template_auth) is built to receive exactly this: its AuthApp opens on the sign-up or sign-in screen.

import 'package:cairn_template_auth/cairn_template_auth.dart';
import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';
import 'package:flutter/material.dart';

void routeAfterOnboarding(BuildContext context, OnboardingResult result) {
  switch (result.accountChoice) {
    case AccountChoice.createAccount:
      _openAuth(context, AuthScreen.signUp, result);
    case AccountChoice.signIn:
      _openAuth(context, AuthScreen.signIn, result);
    case AccountChoice.guest:
      Navigator.of(context).pushReplacementNamed('/home');
  }
}

void _openAuth(BuildContext context, AuthScreen screen, OnboardingResult result) {
  Navigator.of(context).pushReplacement(
    MaterialPageRoute<void>(
      builder: (BuildContext context) => Scaffold(
        body: SafeArea(
          child: AuthApp(
            startOn: screen,
            onAuthenticated: (Session session) {
              // Send result.interests, result.goalId and result.reminderId to
              // your API now that there is an account to attach them to.
              Navigator.of(context).pushReplacementNamed('/home');
            },
          ),
        ),
      ),
    ),
  );
}

Keep the user's answers until the account exists: onboarding finishes before sign-up, so hold the OnboardingResult (in memory or local storage) and apply it in onAuthenticated. For a guest, apply it to a local profile and offer the account later from settings; guests who skipped the permissions can still be asked from your own settings screen.

Why not sign-up inside the flow?

Auth has its own rules (social providers, verification, password reset, a backend). Keeping it a separate template means each can change without touching the other, and either can be used alone.

Use go_router

The template navigates between its own steps with a small cubit, so it needs no router and runs unchanged inside any app. Mount it as one route in yours and use go_router for everything around it:

import 'package:cairn_template_onboarding/cairn_template_onboarding.dart';
import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';
import 'package:shared_preferences/shared_preferences.dart';

GoRouter buildRouter(SharedPreferences prefs, ValueNotifier<bool> seen) {
  return GoRouter(
    initialLocation: '/home',
    refreshListenable: seen,
    redirect: (BuildContext context, GoRouterState state) {
      final bool onboarding = state.matchedLocation == '/onboarding';
      if (!seen.value && !onboarding) return '/onboarding';
      if (seen.value && onboarding) return '/home';
      return null;
    },
    routes: <RouteBase>[
      GoRoute(
        path: '/onboarding',
        builder: (BuildContext context, GoRouterState state) => Scaffold(
          body: SafeArea(
            child: OnboardingApp(
              progressStore: SharedPreferencesProgressStore(prefs),
              permissionService: const PermissionHandlerService(),
              onCompleted: (OnboardingResult result) async {
                await prefs.setBool('onboarding.seen', true);
                seen.value = true; // the redirect now allows leaving
                if (!context.mounted) return;
                switch (result.accountChoice) {
                  case AccountChoice.createAccount:
                    context.go('/sign-up');
                  case AccountChoice.signIn:
                    context.go('/sign-in');
                  case AccountChoice.guest:
                    context.go('/home');
                }
              },
            ),
          ),
        ),
      ),
      GoRoute(path: '/home', builder: (c, s) => const HomeScreen()),
      GoRoute(path: '/sign-up', builder: (c, s) => const SignUpScreen()),
      GoRoute(path: '/sign-in', builder: (c, s) => const SignInScreen()),
    ],
  );
}

// Seed it from storage once, before runApp:
final ValueNotifier<bool> seen =
    ValueNotifier<bool>(prefs.getBool('onboarding.seen') ?? false);
Order matters

Set seen.value = true after the flag is saved, and before context.go: the redirect runs on every change and would otherwise bounce you back to /onboarding.

Make each step a real route

Only do this if you need deep links to a step or a browser back button on web. It means editing the template (use the copy install). This is a sketch of where to cut; the template does not ship it:

  1. core/presentation/navigation/onboarding_navigation_cubit.dart: keep the cubit as the source of truth, but have the shell listen to it and call context.go('/onboarding/${step.name}') from a BlocListener.
  2. presentation/shell/onboarding_shell.dart: replace the AnimatedSwitcher body with the router's child (a ShellRoute whose builder returns the shell and whose child routes build each *View); the views read the session cubits by context.read and do not care how they were reached.
  3. presentation/flow/bloc/onboarding_cubit.dart: on a deep link, call load() and then set the step from the route, instead of begin(). startAtStep already does this for a first build.

Everything else (use cases, mappers, cubits, tests) is untouched, which is the point of keeping navigation in one small cubit.

Localisation

There are two kinds of text, and they are localised differently.

  • Content (page titles and bodies, permission copy, interests, goals, reminder labels, step headings, image descriptions) comes from the flow JSON. Serve the JSON for the user's locale. OnboardingApp reads its data source once, so give it a key tied to the locale and it reloads when the language changes; saved progress carries over because it stores ids, not words.
  • Chrome (Next, Get started, Continue, Skip, Allow, Back, Start, the validation messages) is a short list of strings in the views. Replace each literal with your AppLocalizations lookup.
class LocalizedFlowDataSource implements FlowRemoteDataSource {
  const LocalizedFlowDataSource(this.locale);

  final Locale locale;

  static const Map<String, Map<String, Object?>> _byLanguage =
      <String, Map<String, Object?>>{
    'en': InMemoryFlowRemoteDataSource.content,
    'fr': frenchContent, // same keys, translated values
  };

  @override
  Future<Map<String, Object?>> fetchFlow() async =>
      _byLanguage[locale.languageCode] ?? InMemoryFlowRemoteDataSource.content;
}

// Rebuild the flow when the language changes:
OnboardingApp(
  key: ValueKey<Locale>(locale),
  flowDataSource: LocalizedFlowDataSource(locale),
  progressStore: store,
)

Layouts already cope with longer words: buttons and chips size to their label, headings wrap, and every screen scrolls under a pinned footer. Right-to-left layouts have not been verified: the back chevron and the top bar use fixed left and right positions, so check them if you ship an RTL locale.

Accessibility

  • Every control is named. Icon buttons carry a label ("Back"); buttons that need more context than their text have one ("Allow notifications", "Skip this step", "Open settings to allow location"). The progress bar reads "Onboarding progress, step 2 of 5".
  • Headings are headings. Each screen's title and each page title is announced as a header; the page indicator is one label ("Page 2 of 4") rather than four dots.
  • Images are described. The photographs carry the imageLabel from the content and are otherwise hidden from the tree. Decorative marks are excluded.
  • State is not colour alone. A chosen interest shows a tick as well as a fill; a refused permission shows an icon and words; errors have an icon and are live regions, so they are announced when they appear.
  • Targets are at least 44 × 44. Cairn's buttons are 32 to 40 px, so each is wrapped in TouchTarget, which adds an invisible margin that triggers the same action without adding a second semantic node. The one exception is the reminder CairnSelect, which is Cairn's own 36 px control.
  • Focus order follows reading order: back, progress, skip, the screen's content, then its actions. Cairn controls are keyboard focusable, activate on Space and Enter and show a ring on keyboard focus.
  • Reduced motion. When MediaQuery.disableAnimations is true the step transition, the page change, the splash fade, the dots, the progress bar and the step markers are all instant, and the splash holds for 400 ms instead of 1.4 s. Nothing in the template loops.
  • Large text. Every screen scrolls and keeps its main action pinned. At very large sizes the step labels are dropped (the numbered markers and the heading remain) so three labels never collide.
  • Back. Swipe, the Back button and the platform back gesture all step backwards through pages and parts before leaving a step.

Test with TalkBack and VoiceOver on a device: the template is built to be correct by construction, but only a screen reader tells you how it sounds.

Testing

In the template's folder:

flutter pub get
dart format .
flutter analyze --fatal-infos --fatal-warnings
flutter test

The suite has three layers: domain (the content mapper, progress mapping and repair, the step rules, interest validation, the use cases), session (the cubits wired through the real container, no widgets) and widget tests that mount OnboardingApp at 320, 360 and 700 px, light and dark, and play the whole journey (skip, next through the pages, allow and deny, validation, goal, finish, resume after a simulated restart), plus the reduced-motion path and large text. Flutter fails a test on any RenderFlex overflow, so passing at every width also means no overflow.

Use small tester.pump(Duration) steps, never pumpAndSettle: Cairn has repeating animations, so it would never return. The splash holds for 1.4 s, so pump about 20 steps of 100 ms (or pass startAtStep).

testWidgets('Start reports the saved choices', (WidgetTester tester) async {

Keep the in-memory sources for tests: pass InMemoryProgressStore and DemoPermissionService(answers: {PermissionKind.location: PermissionStatus.denied}) to drive the refusal path. To simulate the app being closed and re-opened, unmount (pumpWidget(const SizedBox.shrink())) and mount again with the same store.

The template's tests load Geist from the Cairn site checkout when they can find it (test/flutter_test_config.dart), so text has real metrics. Without a real font, Flutter draws every glyph as a wide box and reports overflows that production text never has; load your app's font in your own flutter_test_config.dart the same way.

Troubleshooting

"No OnboardingScope above this context"

You built a view or ViewModelBuilder outside OnboardingApp. Mount OnboardingApp (it provides the scope), or wrap your tree in an OnboardingScope with a locator from createOnboardingLocator().

Everything is black and white and unstyled

The host app has no CairnTheme. Use CairnTheme.materialTheme(...) or add CairnTheme.light to ThemeData.extensions.

The photographs are grey panels

The asset did not load. With the package install, check the image path matches a file in the package's assets/images/. With the copy install, make sure OnboardingPackage.name is null and the folder is declared in your pubspec.yaml. Run flutter clean after adding assets.

It does not resume

The default store is in memory. Pass a progressStore that persists (see Persist progress). Also check that your gate does not re-create the store with a different key.

Permissions are always "Allowed" and there is no system prompt

That is DemoPermissionService, the default. Pass your own permissionService.

The splash never goes away

It waits for the content. If loading fails it shows a retry; if your data source never completes (no timeout on a request) it waits forever. Add a timeout and fall back to the built-in content.

Loading fails with a TypeError or FormatException

The JSON has a missing required key or a value of the wrong type. Run it through FlowMapper.fromJson in a test; the stack trace names the key.

Start takes me back to the personalise step

The saved answers do not satisfy the rules (for example a restored state with fewer than minInterests). This is intentional: the host never receives a half-answered result.

The select's menu is hidden behind something

CairnSelect opens in the nearest Overlay. Mount the template under a MaterialApp (or WidgetsApp) so one exists.

"RenderFlex overflowed" in my tests

Flutter's test font is wide. Load your real font in test/flutter_test_config.dart and set fontFamily on the test theme.

Where do I report a bug?

Open an issue on the cairn_site repository with the Flutter and cairn_ui versions.

Migration notes

When you…Do this
Upgrade cairn_ui to a new minorBump the constraint, run flutter analyze. Components added in a minor never break this template; read the library's CHANGELOG for renames.
Change the saved shape (add a field to OnboardingProgress)Update ProgressMapper and bump ProgressMapper.version. Users with older saved data start over once; nothing crashes.
Reword content that is already liveChange labels freely; keep ids. Ids are what users' saved progress refers to.
Remove an interest, goal, reminder, page or step that is liveJust remove it. ResumeProgress drops what no longer exists and clamps the page index, so a returning user lands somewhere valid.
Move from the copied source to the packageDelete your copy, add the dependency, change imports back to package:cairn_template_onboarding/…, set OnboardingPackage.name back (the package's default), and move your edits (usually only the content map and the brand constants) into your own data source and wrapper.
Pull template updates into a copyDiff templates/onboarding/lib between your last sync tag and the new one; because dependencies point inwards, changes are almost always inside a single layer.
Change state managementCubits are plain streams of immutable states. Views call cubit.method() and read state, so Riverpod or Provider can replace BlocBuilder view by view.
