Shop template

A mobile e-commerce app built only from cairn_ui: storefront, product pages, cart, a four-step checkout, order history and a profile. This page is the manual and the tutorial. It works offline and prints cleanly.

1. Overview & architecture

The package is cairn_template_shop; the entry widget is ShopApp, exported from package:cairn_template_shop/cairn_template_shop.dart. Code is organised as clean architecture: the layers sit at the top of lib/ and each layer is split by feature (catalog, saved, cart, checkout, orders, profile).

lib/
  shop_app.dart                      ShopApp (entry widget)
  core/
    infrastructure/di/               shop_injection.dart: the get_it container
    presentation/                    navigation cubit, shared widgets, ViewModel
  common/
    constants/                       categories, shipping policy, promo codes/slides
    utils/                           money, dates, luhn
  data/<feature>/
    remote/                          data sources: return decoded JSON maps
    repositories/                    implement the domain interfaces
  domain/<feature>/
    models/  mappers/  repositories/  use_cases/
  presentation/<feature>/
    bloc/  view_models/  views/  widgets/
  presentation/shell/                providers, dock, tab composition

dependencies point inwards:
  presentation  -->  domain  <--  data
  (domain depends on nothing but Dart and common)

The rules, in short:

  • Data sources return decoded JSON maps, as a REST client would. Mappers in domain/<feature>/mappers/ turn them into models.
  • Use cases do one job each and are pure where possible (CalculateCartTotals, SortProducts, ValidatePaymentDetails).
  • Session cubits (navigation, catalogue, saved, cart, checkout, orders, profile) are lazy singletons provided by ShopProviders. Screen cubits (product page, suggestions) are created and closed by a view model through ViewModelBuilder.
  • Views never touch the container. Registration is written out by hand in shop_injection.dart: no code generation.
  • Only cairn_ui widgets and tokens, plus Material Icons for glyphs Cairn lacks.

3. Install

As a package (path or git)

Images resolve as packages/cairn_template_shop/assets/images/..., so nothing else is needed.

# pubspec.yaml of your app
dependencies:
  cairn_template_shop:
    path: ../cairn_template_shop
  # or
  # cairn_template_shop:
  #   git:
  #     url: https://example.com/your/repo.git
  #     path: templates/shop

By copying lib/ and assets/

  1. Copy lib/ into your app (for example into lib/shop/) and assets/images/ into your assets/.
  2. Add cairn_ui, equatable, flutter_bloc and get_it to your pubspec.yaml and declare the assets.
  3. In lib/common/constants/shop_package.dart set the package name to null, so images load from your app:
abstract final class ShopPackage {
  static const String? name = null; // was: String name = 'cairn_template_shop'
}
# pubspec.yaml of your app
flutter:
  assets:
    - assets/images/

The template's imports are relative, so a copied folder keeps working wherever you put it.

The shipped line is static const String name = 'cairn_template_shop';. Change the type to String? when you set it to null, as above.

4. Mount it

A complete main.dart:

import 'package:cairn_template_shop/cairn_template_shop.dart';
import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/material.dart';

void main() => runApp(const MyApp());

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      debugShowCheckedModeBanner: false,
      theme: CairnTheme.materialTheme(CairnTheme.light),
      darkTheme: CairnTheme.materialTheme(CairnTheme.dark),
      home: const Scaffold(
        body: SafeArea(child: ShopApp()),
      ),
    );
  }

ShopApp takes the size it is given, from 320 by 640 up. Under 700 px wide it fills the space; from 700 px up its content is a centred column 480 px wide. In a phone mockup:

Behaviour worth knowing: CAIRN10 is 10% off the subtotal, matched case-insensitively. Free standard shipping is judged on the subtotal after the discount. Express always costs the express rate. To add a code, add an entry to the map:

static const Map<String, int> percentOff = <String, int>{
  'CAIRN10': 10,
  'WELCOME20': 20,
};
Promo codes in a client-side map are visible to anyone. In production the backend must validate and price every code; the client should only display the result.

7. Branding & theming

Every colour, radius and text style resolves through CairnTheme, so branding is one theme. Customise with copyWith and pass it to CairnTheme.materialTheme:

final CairnTheme brand = CairnTheme.light.copyWith(
  primary: const Color(0xFF0B6E4F),
  primaryForeground: const Color(0xFFFFFFFF),
  radius: 14,              // base corner radius (the default is 10)
  fontFamily: 'Inter',
);

MaterialApp(
  theme: CairnTheme.materialTheme(brand),
  darkTheme: CairnTheme.materialTheme(
    CairnTheme.dark.copyWith(primary: const Color(0xFF5EE0AE), fontFamily: 'Inter'),
  ),
  home: const Scaffold(body: SafeArea(child: ShopApp())),

Fonts are declared in your app's pubspec.yaml as usual (flutter: fonts:); set fontFamily to the family name. The Cairn site uses Geist.

The promo carousel text is white over a dark gradient in both themes, by design, because it sits on photographs. Sale badges use the destructive colour and New badges the primary colour.

8. Connect a real backend

Each data source is an interface returning decoded JSON. To go live, implement the interface, register it in shop_injection.dart in place of the InMemory one, and change the mapper only if your JSON differs. Add http to your pubspec.yaml:

dependencies:
  http: ^1.2.0

A REST data source

One small client holds the base URL and the auth token; the data sources use it. Create lib/data/shop_api.dart:

import 'dart:convert';

import 'package:http/http.dart' as http;

/// Thrown when the API answers with an error status.
class ShopApiException implements Exception {
  ShopApiException(this.statusCode, this.body);
  final int statusCode;
  final String body;

  @override
  String toString() => 'ShopApiException($statusCode): $body';
}

class ShopApi {
  ShopApi({
    required this.baseUrl,
    required this.tokenProvider,
    http.Client? client,
  }) : _client = client ?? http.Client();

  final Uri baseUrl;
  final Future<String?> Function() tokenProvider;
  final http.Client _client;

  Future<Object?> getJson(String path) async {
    final http.Response r = await _client
        .get(baseUrl.resolve(path), headers: await _headers())
        .timeout(const Duration(seconds: 15));
    return _decode(r);
  }

  Future<Object?> postJson(String path, Map<String, Object?> body) async {
    final http.Response r = await _client
        .post(
          baseUrl.resolve(path),
          headers: await _headers(),
          body: jsonEncode(body),
        )
        .timeout(const Duration(seconds: 15));
    return _decode(r);
  }

  Future<Map<String, String>> _headers() async {
    final String? token = await tokenProvider();
    return <String, String>{
      'Content-Type': 'application/json',
      'Accept': 'application/json',
      if (token != null) 'Authorization': 'Bearer $token',
    };
  }

  Object? _decode(http.Response r) {
    if (r.statusCode < 200 || r.statusCode >= 300) {
      throw ShopApiException(r.statusCode, r.body);
    }
    return r.body.isEmpty ? null : jsonDecode(r.body);
  }
}

Then the catalogue and orders data sources, implementing the template's interfaces exactly:

import 'package:cairn_template_shop/data/catalog/remote/product_remote_data_source.dart';
import 'package:cairn_template_shop/data/orders/remote/order_remote_data_source.dart';

import 'shop_api.dart';

class RestProductRemoteDataSource implements ProductRemoteDataSource {
  RestProductRemoteDataSource(this._api);
  final ShopApi _api;

  @override
  Future<List<Map<String, Object?>>> fetchProducts() async {
    final Object? json = await _api.getJson('products');
    return (json! as List<Object?>).cast<Map<String, Object?>>();
  }
}

class RestOrderRemoteDataSource implements OrderRemoteDataSource {
  RestOrderRemoteDataSource(this._api);
  final ShopApi _api;

  @override
  Future<List<Map<String, Object?>>> fetchOrders() async {
    final Object? json = await _api.getJson('orders');
    return (json! as List<Object?>).cast<Map<String, Object?>>();
  }

  @override
  Future<Map<String, Object?>> createOrder(Map<String, Object?> order) async {
    final Object? json = await _api.postJson('orders', order);
    return json! as Map<String, Object?>;
  }
}

The JSON your API returns must match the fields in section 5 for products. For orders it must match OrderMapper: id, status (processing, shipped or delivered), placedAt, estimatedDelivery, cardLast4, optional promoCode, a shipping object, a totals object (itemCount, subtotal, discount, shipping, delivery) and lines (productId, variant, quantity). If yours differs, edit the mapper, not the views.

Register it

In createShopLocator() in lib/core/infrastructure/di/shop_injection.dart, swap the registrations. Give the function the pieces it needs as parameters so the host app supplies them:

GetIt createShopLocator({
  Duration catalogLatency = Duration.zero,
  ShopApi? api,
}) {
  final GetIt g = GetIt.asNewInstance();

  if (api != null) {
    g
      ..registerLazySingleton<ProductRemoteDataSource>(
        () => RestProductRemoteDataSource(api),
      )
      ..registerLazySingleton<OrderRemoteDataSource>(
        () => RestOrderRemoteDataSource(api),
      );
  } else {
    g
      ..registerLazySingleton<ProductRemoteDataSource>(
        () => InMemoryProductRemoteDataSource(latency: catalogLatency),
      )
      ..registerLazySingleton<OrderRemoteDataSource>(
        InMemoryOrderRemoteDataSource.new,
      );
  }
  // ... the rest of the registrations stay as they are.

Pass the same api through a field on ShopApp (add final ShopApi? api; and hand it to createShopLocator in _ShopAppState).

Auth token

tokenProvider is called per request, so it can read secure storage or refresh an expired token. Keep tokens in flutter_secure_storage or your auth SDK, never in the template's in-memory sources. Account data comes from ProfileRemoteDataSource: implement readAccount, signIn and signOut against your auth service the same way (those interfaces are synchronous in the template because the stand-ins are in memory; make them return Future and add await in ProfileRepositoryImpl).

Error handling

  • Catalogue: CatalogCubit.load catches any error and moves to CatalogStatus.failed; the storefront shows an alert with a Try again button that calls load again.
  • Placing an order: CheckoutCubit.placeOrder catches errors, stays on the review step with the form intact and shows "We could not place your order. Please try again." The cart is only cleared after the order is stored.
  • Timeouts, retries and offline handling belong in ShopApi; it throws ShopApiException for HTTP errors.
  • Product detail, cart and recommendation calls go through ProductRepository, which caches the catalogue after the first successful load. Add invalidation (or pull to refresh) if your catalogue changes while the app runs.

Firebase / Firestore sketch

The same shape works with Firestore. Documents become the JSON maps; add the document id as id:

import 'package:cloud_firestore/cloud_firestore.dart';

class FirestoreProductRemoteDataSource implements ProductRemoteDataSource {
  FirestoreProductRemoteDataSource(this._db);
  final FirebaseFirestore _db;

  @override
  Future<List<Map<String, Object?>>> fetchProducts() async {
    final QuerySnapshot<Map<String, dynamic>> snap =
        await _db.collection('products').get();
    return <Map<String, Object?>>[
      for (final QueryDocumentSnapshot<Map<String, dynamic>> d in snap.docs)
        <String, Object?>{...d.data(), 'id': d.id},
    ];
  }
}

class FirestoreOrderRemoteDataSource implements OrderRemoteDataSource {
  FirestoreOrderRemoteDataSource(this._db, this._uid);
  final FirebaseFirestore _db;
  final String _uid;

  CollectionReference<Map<String, dynamic>> get _orders =>
      _db.collection('users').doc(_uid).collection('orders');

  @override
  Future<List<Map<String, Object?>>> fetchOrders() async {
    final QuerySnapshot<Map<String, dynamic>> snap =
        await _orders.orderBy('placedAt', descending: true).get();
    return <Map<String, Object?>>[
      for (final QueryDocumentSnapshot<Map<String, dynamic>> d in snap.docs)
        <String, Object?>{...d.data(), 'id': d.id},
    ];
  }

  @override
  Future<Map<String, Object?>> createOrder(Map<String, Object?> order) async {
    // Prefer a Cloud Function that numbers the order and sets the status.
    final DocumentReference<Map<String, dynamic>> ref = await _orders.add(order);
    return <String, Object?>{...order, 'id': ref.id, 'status': 'processing'};
  }
}

Store dates as ISO-8601 strings (not Timestamps) or convert them in the data source, because the mappers parse strings. Secure the collections with Firestore rules; the client must never be able to set an order's status or totals.

9. Payments

The template never processes cards. The Payment step is a demo: it checks the format (including the Luhn checksum and expiry), keeps the card in memory only while the form is open, stores only the last four digits on the order and clears the card when the order is placed. Nothing leaves the device. Do not ship it as a payment form.

To take real payments, replace the card form with your provider's UI so card numbers never touch your code or your server.

Stripe PaymentSheet

Your server creates a PaymentIntent for the order total and returns its client secret; the app presents Stripe's sheet. With flutter_stripe:

import 'package:flutter_stripe/flutter_stripe.dart';

abstract interface class PaymentGateway {
  /// Charges [amountCents]; returns the provider's payment id.
  Future<String> pay(int amountCents);
}

class StripePaymentGateway implements PaymentGateway {
  StripePaymentGateway(this._api);
  final ShopApi _api;

  @override
  Future<String> pay(int amountCents) async {
    final Map<String, Object?> intent =
        (await _api.postJson('payments/intent', <String, Object?>{
              'amount': amountCents,
              'currency': 'usd',
            }))!
            as Map<String, Object?>;
    await Stripe.instance.initPaymentSheet(
      paymentSheetParameters: SetupPaymentSheetParameters(
        paymentIntentClientSecret: intent['clientSecret']! as String,
        merchantDisplayName: 'Your shop',
      ),
    );
    await Stripe.instance.presentPaymentSheet(); // throws if cancelled/declined
    return intent['id']! as String;
  }
}

Wire it in four steps:

  1. Put PaymentGateway in domain/checkout/repositories/ and the Stripe class in data/checkout/; register it in shop_injection.dart.
  2. Give PlaceOrder the gateway. Call pay(totals.total * 100) after computing totals and before _orders.place; pass the returned payment id in the OrderDraft so your backend can reconcile. A thrown error is already handled by CheckoutCubit.
  3. Remove the payment step: delete PaymentStep and CheckoutStep.payment, drop ValidatePaymentDetails and PaymentDetails, and shorten the CairnSteps list in CheckoutView and OrderConfirmationView. Keep the Review step as the last step before the sheet opens.
  4. Confirm the payment on your server with Stripe's webhook before marking the order paid. The client's success is not proof.

A hosted checkout

For Stripe Checkout, Shopify or PayPal, have the backend return a session URL, open it with url_launcher (or an in-app web view), and treat the redirect back as the confirmation trigger. The flow is the same: the Review step becomes "Pay", and PlaceOrder is called only once the backend says the payment succeeded.

10. Swap in-template navigation for go_router

The shop navigates with ShopNavigationCubit (a tab, plus an optional product id or order id on top) so it runs inside any app. Views only call four methods: selectTab, openProduct, openOrder and back. To use go_router, keep those calls and make them drive the router.

import 'package:cairn_template_shop/core/presentation/navigation/shop_navigation_cubit.dart';
import 'package:go_router/go_router.dart';

class RouterNavigationCubit extends ShopNavigationCubit {
  RouterNavigationCubit(this._router);
  final GoRouter _router;

  @override
  void selectTab(ShopTab tab) => _router.go('/${tab.name}');

  @override
  void openProduct(String id) => _router.push('/product/$id');

  @override
  void openOrder(String id) => _router.push('/orders/$id');

  @override
  void back() => _router.pop();
}

Register it in shop_injection.dart instead of ShopNavigationCubit.new (pass the router into createShopLocator), then describe the screens as routes. The views are public classes:

final GoRouter router = GoRouter(
  initialLocation: '/shop',
  routes: <RouteBase>[
    ShellRoute(
      builder: (BuildContext context, GoRouterState state, Widget child) =>
          MyShopFrame(child: child), // your scaffold with a CairnDock
      routes: <RouteBase>[
        GoRoute(path: '/shop', builder: (_, __) => const StorefrontView()),
        GoRoute(path: '/saved', builder: (_, __) => const SavedView()),
        GoRoute(path: '/cart', builder: (_, __) => const CartTab()),
        GoRoute(path: '/profile', builder: (_, __) => const ProfileView()),
        GoRoute(
          path: '/product/:id',
          builder: (_, GoRouterState s) =>
              ProductDetailView(productId: s.pathParameters['id']!),
        ),
        GoRoute(
          path: '/orders/:id',
          builder: (_, GoRouterState s) =>
              OrderDetailView(orderId: s.pathParameters['id']!),
        ),
      ],
    ),
  ],
);

Put the container and providers above the router, and load the session cubits once, as ShopApp does:

final GetIt locator = createShopLocator(router: router);

MaterialApp.router(
  routerConfig: router,
  builder: (BuildContext context, Widget? child) => ShopScope(
    locator: locator,
    child: ShopProviders(locator: locator, child: child!),
  ),
);

Notes: ShopShell and its dock are only a switch over the navigation state, so MyShopFrame replaces them (build a CairnDock that calls context.go). The cart tab's internal step (cart, checkout, confirmation) is state in CheckoutCubit, not a route; if you want URLs for the steps, add routes that call CheckoutCubit.begin and goTo. The router replaces state.tab, so read the active tab from GoRouterState for the dock's selected index.

11. Localisation & currency

Currency

Every price goes through formatMoney in lib/common/utils/money.dart. It prints dollars, without cents for whole amounts. Replace its body with intl:

import 'package:intl/intl.dart';

String formatMoney(double value) {
  final NumberFormat f = NumberFormat.simpleCurrency(name: 'EUR');
  return value == value.roundToDouble()
      ? NumberFormat.currency(
          name: 'EUR', symbol: '€', decimalDigits: 0).format(value)
      : f.format(value);
}

Also change the literal dollar amounts in HelpTopics (help_topics.dart) and check TotalsSummary, which prefixes discounts with a minus sign, if your currency puts its symbol after the number. Shipping thresholds are numbers in ShippingPolicy; set them in your currency.

Dates

formatDate and formatShortDate in lib/common/utils/dates.dart use English month and weekday names. Swap them for DateFormat.yMMMd(locale) and DateFormat.MMMEd(locale).

Text

User-facing strings are English literals in the views and widgets, and the constants files (promo_slides.dart, help_topics.dart, ProductSort.label, OrderStatus.label, DeliveryMethod.label) plus validator messages in the use cases. A practical route:

  1. Move the labels held in enums and constants behind a function that takes BuildContext or an AppLocalizations, in the presentation layer (domain must stay free of Flutter).
  2. Turn validator messages into error codes (an enum) returned by the use cases and translate them in the step widgets. The tests already assert on the keys (ShippingField, PaymentField), so only the message assertions change.
  3. Run grep -rn "Text('" lib/presentation to find the remaining literals.

Right-to-left layouts use directional widgets from Flutter and Cairn; check the carousel and the dock with a RTL Directionality.

Rules for widget tests in this package:

  • Never pumpAndSettle. Cairn has repeating animations (spinner, skeleton, progress) that never settle. Pump small steps with pumpFrames.
  • AnimatedSwitcher keeps the old page mounted for a few frames after a navigation; pump 6 to 10 frames before asserting that a page is gone.
  • Mount with ShopApp(catalogLatency: Duration.zero) (the harness does) so no timers are pending.
  • Flutter's test font draws every glyph as a full em square, far wider than Geist. The harness scales text by 0.6 so 320 px layouts do not overflow in tests only. If you load Geist in your own tests, remove the scale.
  • Lists build lazily: scroll to an item with reveal before asserting or tapping it.

To test your own data source, run the same journey with it registered; the session tests build the real container with createShopLocator() and show how.

13. Troubleshooting & FAQ

Images show as grey boxes

If you copied lib/ and assets/ into your app, ShopPackage.name must be null and assets/images/ must be declared in your pubspec.yaml. As a package dependency leave the name as it is. Check the asset path in the JSON starts with assets/images/ and the file exists; the seed-data test fails otherwise.

"GetIt: Object/factory with type X is not registered"

You added a use case or cubit but did not register it. Add it to createShopLocator() in shop_injection.dart. Use cases are factories; data sources and repositories are lazy singletons; session cubits are lazy singletons with dispose: (c) => c.close().

The storefront shows skeletons forever

The catalogue future never completed. With the in-memory source, check catalogLatency. With your own, make sure fetchProducts returns or throws (a throw shows the Try again alert).

The cart and orders are empty after a restart

The in-memory data sources live only as long as the app. Persist through your backend, or implement the data source with shared_preferences storing the same JSON.

Overflow errors only in tests

The test font is wider than Geist; see section 12.

pumpAndSettle times out

Do not use it here; see section 12.

A product appears under All but not under its category

Its category string does not match an entry of ProductCategories.values (case-sensitive).

Why is the catalogue a session cubit?

So the shopper's search, category and sort survive opening a product and coming back. Screen cubits (product page, suggestions) are created per visit.

Can I use it inside an app that has its own router?

Yes. The shop keeps its own navigation state and renders inside whatever widget you put ShopApp in. Use section 10 only if you want its screens to be routes.

How do I remove a feature?

Delete the feature's folders in each layer, its registrations in shop_injection.dart, its provider in ShopProviders and the places that read it (the shell's tab, the storefront's header). The analyzer lists what is left.

Upgrading cairn_ui

  • The template depends on cairn_ui ^0.2.0. For a newer minor release, bump the constraint, run flutter pub upgrade cairn_ui, then flutter analyze; the analyzer points at any renamed parameter.
  • Components used: CairnBadge, CairnIndicator, CairnAvatar, CairnRating, CairnSelect, CairnSkeleton, CairnAccordion, CairnToggleGroup, CairnRadioGroup, CairnSteps, CairnTimeline, CairnDock, CairnList, CairnStats, CairnProgress, CairnAlert, CairnInput, CairnSwitch, CairnButton, CairnSeparator, CairnRadialProgress, CairnSpinner.   • Cairn's radio item lays its label out without a width limit; ShippingStep gives it one. If a future release bounds the label, that wrapper can go.
