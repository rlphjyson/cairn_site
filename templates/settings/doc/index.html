Settings template

Mobile settings screens built only from cairn_ui: a searchable home, profile, appearance, notifications, privacy and security, language, storage, help, about and a danger zone. This guide takes you from copy it in to shipping it with your own backend, your own list of settings and your own account flow.

Overview

The template is a Flutter package, cairn_template_settings, that exposes one widget, SettingsApp, and a handful of types your app implements or receives. It contains these screens:

  • Home – a title, a search field, a profile card and the categories in four groups (Account, Preferences, Data and support, Session). Search matches titles, keywords, descriptions and section names and jumps straight to the right page.
  • Edit profile – name, username (checked for availability as you type), email, bio and an avatar preset, with inline validation and a “Discard changes?” guard.
  • Appearance – Light, Dark or System, four text sizes with a live sample, an accent colour and Reduce motion. Changes apply to the whole template at once.
  • Notifications – a master switch, categories, channel, digest and quiet hours; an alert with Open settings when the operating system has refused permission.
  • Privacy and security – biometric lock, two-factor authentication (setup sheet with a secret key and a six-digit code), change password with a strength meter, active sessions, export my data and blocked users.
  • Language and region – language, region, date and time formats and units, with a preview.
  • Storage and data – a usage meter, clear cache, Wi-Fi only and auto-delete.
  • Help and About – FAQ, a contact form, copyable version, licences, Terms and Privacy links and a star rating.
  • Danger zone – Sign out, Deactivate account and Delete account (type DELETE, then confirm again).

From 600 px wide the screens become a two-pane master/detail layout: the categories on the left, the selected category on the right. It is organised as clean architecture by layer, then by feature, with flutter_bloc for state and get_it for dependency injection. Nothing is generated.

lib/ ├─ settings_app.dart entry widget (SettingsApp) ├─ core/ │ ├─ infrastructure/ get_it registration (di/), the host's callbacks, unsaved-changes guard │ └─ presentation/ navigation cubit, ViewModel, reusable rows and frames, appearance ├─ common/ layout, text sizes, FAQ, subjects, avatars, helpers ├─ data/<feature>/ SettingsDataSource (+ in-memory demo), repositories ├─ domain/<feature>/ models, mappers, registry, repository interfaces, use cases └─ presentation/<feature>/ bloc, view models, views, widgets (+ shell/)
The one rule to remember

Dependencies point inwards: presentation → domain ← data. What settings exist is a list (the SettingsRegistry). Where they are stored is one object (SettingsDataSource). What happens when something changes is a callback. You pass all three to SettingsApp and never fork the template to integrate it.

The template has no platform code, no plugins and no assets of its own. Storage, the account and the platform are interfaces and callbacks you provide, so adding or swapping a plugin never touches the template.

Install

A. As a package (recommended)

Keeping it a package means you can pull in fixes later with a version bump.

# pubspec.yaml
dependencies:
  cairn_ui: ^0.2.0
  cairn_template_settings:
    git:
      url: https://github.com/rlphjyson/cairn_site.git
      path: templates/settings
      ref: main            # pin a tag or commit for production
  shared_preferences: ^2.3.0

Or, from a local checkout: path: ../cairn_site/templates/settings. Everything the package needs for the common cases is exported from package:cairn_template_settings/cairn_template_settings.dart: SettingsApp, SettingsDataSource, InMemorySettingsDataSource, Profile, NotificationPermission, SettingsLink, SettingsPage, SettingsSection, SettingsRegistry, defaultSettingsRegistry, SettingIds and the five definition classes (ToggleSetting, ChoiceSetting, SliderSetting, ActionSetting, LinkSetting) with ChoiceOption, ChoiceStyle, SettingKind and SettingDefinition.

B. Copy the source into your app

Use this when you want to change screens, add a category or edit the constants (see Add a section and Change the copy).

  1. Copy templates/settings/lib/ into lib/settings/ of your app. Delete cairn_template_settings.dart if you do not want the barrel.
  2. Add cairn_ui, flutter_bloc, get_it and equatable to your pubspec.yaml. There are no assets to declare.
  3. Rewrite the package:cairn_template_settings/… imports to your app's package name (a find-and-replace). Files inside the template use relative imports, so only your own references change.
  4. Copy test/ too (the harness in test/support/ is useful) and rewrite its imports the same way.

Mount it

The template reads fonts and radii from CairnTheme, so the host app must provide one. Below is a complete main.dart: it keeps the settings in shared_preferences (see Persist the settings), follows the person's theme choice and handles sign out.

import 'package:cairn_template_settings/cairn_template_settings.dart';
import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';

Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  final SharedPreferences prefs = await SharedPreferences.getInstance();
  runApp(MyApp(prefs: prefs));
}

class MyApp extends StatefulWidget {
  const MyApp({super.key, required this.prefs});

  final SharedPreferences prefs;

  @override
  State<MyApp> createState() => _MyAppState();
}

class _MyAppState extends State<MyApp> {
  ThemeMode _mode = ThemeMode.system;

  // One data source for the whole app session. PreferencesSettingsDataSource
  // is defined in "Persist the settings" below.
  late final PreferencesSettingsDataSource _source =
      PreferencesSettingsDataSource(widget.prefs);

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Daybreak',
      themeMode: _mode,
      theme: CairnTheme.materialTheme(CairnTheme.light),
      darkTheme: CairnTheme.materialTheme(CairnTheme.dark),
      home: Scaffold(
        body: SafeArea(
          child: SettingsApp(
            settingsDataSource: _source,
            onThemeModeChanged: (ThemeMode mode) => setState(() => _mode = mode),
            onSignOut: () {
              // End the session, then show your sign-in screen.
            },
          ),
        ),
      ),
    );
  }
}

SettingsApp fills whatever space its parent gives it (320 × 640 and up), so put it in a Scaffold body, a CairnMockupPhone or a fixed-height box. Each instance creates its own dependency container and disposes it, so two copies never share state. It needs a MaterialApp (or WidgetsApp) above it for the overlay that dialogs, sheets and select menus open in. Wrap it in a SafeArea as above, since the template draws its own page frame edge to edge.

The screens

phone (< 600 px) tablet (≥ 600 px) ┌───────────────┐ ┌──────────┬────────────────────┐ │ Settings │ tap a row │ Settings │ Appearance │ │ [Search] │ ───────────► │ [Search] │ Theme ( ) ( ) ( ) │ │ [Profile] │ one page at a time │ [Profile]│ Text size ──●── │ │ Appearance › │ back = chevron, │ Appear. │ Accent colour │ │ Notifications │ swipe, system back │ Notific. │ Reduce motion │ │ ... │ │ ... │ │ └───────────────┘ └──────────┴────────────────────┘ 288 px list content up to 560 px

Rules

  • Two panes when the available width is at least SettingsLayout.wideBreakpoint (600) and text is not very large (system text scaled above about 1.35). At large text a tablet falls back to one page at a time, so the list never swallows the page beside it. Choosing a category on the left replaces the page on the right; the first category is selected when nothing is open.
  • Changes are optimistic. Toggling a setting updates the screen at once, calls onSettingChanged (and onThemeModeChanged for the theme), then saves through the data source. If the save throws, the previous value comes back and a toast says “Could not save that change”. A value the registry does not accept is refused with a toast and nothing changes.
  • Reading is forgiving. A missing key, a value of the wrong type and a choice that is no longer offered fall back to the setting's default, and keys with no definition are dropped, so data written by an older or newer build never breaks the app.
  • Back steps from a sub-page (Change password, Active sessions, Blocked users) to its category and from a category to the home. The system back gesture does the same; on the home it is left to your app.
  • Unsaved edits are guarded. If Edit profile has changes, leaving it by the back control, the system back, another category on the tablet or a search result asks “Discard changes?” first.
  • Two-factor. Turning it on opens a sheet with a secret key and a six-digit code; only a correct code sets the switch. Turning it off asks first, calls the data source, then clears the switch.
  • Notifications. The master switch greys out everything below it; quiet hours' start and end are enabled only when quiet hours are on. See Notification permission.
  • Delete account needs the exact word DELETE (case-sensitive) and then a second “This is the last step” confirmation. Deactivate and Sign out ask once.
  • Some switches only record a choice. Biometric lock, Wi-Fi only, auto-delete, quiet hours, language and region are stored and reported through onSettingChanged; enforcing them (calling local_auth, pausing downloads, scheduling silence, translating your app) is your app's job.

Connect a backend

Everything the template asks its backend for goes through one interface, SettingsDataSource. Today the default is InMemorySettingsDataSource, a demo that returns decoded JSON and applies a 300 ms latency so loading and saving states are visible. It has a few rules that exercise the error paths: the usernames admin, root, support and cairn are taken, the current password wrong-password is rejected and the two-factor code is 123456.

The contract

Every method returns what a REST client would hand you after jsonDecode. Mappers in domain/<feature>/mappers/ turn it into models and are the only place that knows the wire format. Reads that fail should throw: the screen shows a retry. Writes that the server refuses should return {"ok": false, "error": "A sentence for the person."}: the sentence is shown as it is. A write that throws shows a generic “Could not …” message.

loadProfile(){"name", "username", "email", "bio", "avatar"} (avatar is a preset id)

checkUsername(username){"available": true}
loadSessions(){"sessions": [{"id", "device", "location", "lastActive" (ISO 8601), "current"}]}

Server-owned values

The settings blob also carries privacy.twoFactor. If your server is the source of truth for two-factor, include the real state in loadSettings ("privacy.twoFactor": user.twoFactorEnabled) so the switch is right after a reinstall. The same goes for anything else the account decides, such as the language.

Persist the settings

The quickest real integration extends the demo and replaces only the calls you care about. This one keeps the setting values in shared_preferences and reports the real app version; profile, sessions and the rest stay on the demo until you replace them.

import 'dart:convert';

import 'package:cairn_template_settings/cairn_template_settings.dart';
import 'package:package_info_plus/package_info_plus.dart';
import 'package:shared_preferences/shared_preferences.dart';

class PreferencesSettingsDataSource extends InMemorySettingsDataSource {
  PreferencesSettingsDataSource(SharedPreferences prefs)
    : _prefs = prefs,
      super(latency: Duration.zero, settings: _stored(prefs));

  static const String _key = 'settings.values';

  final SharedPreferences _prefs;

  static Map<String, Object?> _stored(SharedPreferences prefs) {
    final String? raw = prefs.getString(_key);
    if (raw == null) return <String, Object?>{};
    try {
      return Map<String, Object?>.from(jsonDecode(raw) as Map<Object?, Object?>);
    } on Object {
      return <String, Object?>{}; // unreadable: start from the defaults
    }
  }

  @override
  Future<void> saveSettings(Map<String, Object?> json) async {
    await super.saveSettings(json); // keeps loadSettings in step
    await _prefs.setString(_key, jsonEncode(json));
  }

  @override
  Future<Map<String, Object?>> loadAppInfo() async {
    final PackageInfo info = await PackageInfo.fromPlatform();
    return <String, Object?>{
      'name': info.appName,
      'version': info.version,
      'build': info.buildNumber,
      'licences': <Object?>[
        <String, Object?>{
          'name': 'cairn_ui',
          'licence': 'MIT',
          'summary': 'The component library the screens are built from.',
        },
      ],
    };
  }
}
  • What is saved: {"schema": 1, "values": {...}}, where each value is a bool, a String or an int. None of it is secret.
  • Ids are keys. Setting ids (appearance.themeMode, notifications.messages) are what is stored. Reword titles freely; keep ids stable, or the stored value is lost and the default returns.
  • Per user: if several people share a device, include the user id in your key, and remove it on sign out.
  • Stale keys: keys without a definition are ignored when reading and dropped on the next save.

A REST backend

Implement the whole interface when everything lives on a server. The helper methods keep each call to one line: reads throw on any failure, writes turn a 4xx into the ok: false envelope the screens expect and a 5xx into an exception.

import 'dart:convert';

import 'package:cairn_template_settings/cairn_template_settings.dart';
import 'package:http/http.dart' as http;

class ApiSettingsDataSource implements SettingsDataSource {
  ApiSettingsDataSource(this._client, {required this.baseUrl, required this.token});

  final http.Client _client;

  /// Ends with a slash, for example https://api.example.com/v1/me/
  final Uri baseUrl;
  final String Function() token;

  Map<String, String> get _headers => <String, String>{
    'Authorization': 'Bearer ${token()}',
    'Content-Type': 'application/json',
  };

  Map<String, Object?> _json(String body) => body.isEmpty
      ? <String, Object?>{}
      : Map<String, Object?>.from(jsonDecode(body) as Map<Object?, Object?>);

  Future<http.Response> _send(String method, String path, Object? body) async {
    final http.Request request = http.Request(method, baseUrl.resolve(path))
      ..headers.addAll(_headers);
    if (body != null) request.body = jsonEncode(body);
    return http.Response.fromStream(await _client.send(request));
  }

  /// A read: anything but 2xx throws, so the screen offers a retry.
  Future<Map<String, Object?>> _read(String path, {String method = 'GET', Object? body}) async {
    final http.Response res = await _send(method, path, body);
    if (res.statusCode < 200 || res.statusCode > 299) {
      throw http.ClientException('$method $path failed: ${res.statusCode}');
    }
    return _json(res.body);
  }

  /// A write: 4xx becomes { ok: false, error }, 5xx throws.
  Future<Map<String, Object?>> _write(String method, String path, [Object? body]) async {
    final http.Response res = await _send(method, path, body);
    if (res.statusCode >= 500) {
      throw http.ClientException('$method $path failed: ${res.statusCode}');
    }
    if (res.statusCode >= 400) {
      return <String, Object?>{
        'ok': false,
        'error': _json(res.body)['error'] ?? 'Something went wrong. Please try again.',
      };
    }
    return <String, Object?>{'ok': true, ..._json(res.body)};
  }

  @override
  Future<Map<String, Object?>> loadSettings() => _read('settings');

  @override
  Future<void> saveSettings(Map<String, Object?> json) =>
      _read('settings', method: 'PUT', body: json);

  @override
  Future<Map<String, Object?>> loadAppInfo() => _read('app-info');

  @override
  Future<Map<String, Object?>> loadProfile() => _read('profile');

  @override
  Future<Map<String, Object?>> saveProfile(Map<String, Object?> json) =>
      _read('profile', method: 'PUT', body: json);

  @override
  Future<Map<String, Object?>> checkUsername(String username) =>
      _read('usernames/${Uri.encodeComponent(username)}');

  @override
  Future<Map<String, Object?>> loadSessions() => _read('sessions');

  @override
  Future<Map<String, Object?>> revokeSession(String sessionId) =>
      _write('DELETE', 'sessions/$sessionId');

  @override
  Future<Map<String, Object?>> revokeOtherSessions() =>
      _write('DELETE', 'sessions?others=true');

  @override
  Future<Map<String, Object?>> changePassword({
    required String current,
    required String next,
  }) => _write('POST', 'password', <String, Object?>{'current': current, 'next': next});

  @override
  Future<Map<String, Object?>> beginTwoFactor() =>
      _read('two-factor', method: 'POST');

  @override
  Future<Map<String, Object?>> verifyTwoFactor(String code) =>
      _write('POST', 'two-factor/verify', <String, Object?>{'code': code});

  @override
  Future<Map<String, Object?>> disableTwoFactor() => _write('DELETE', 'two-factor');

  @override
  Future<Map<String, Object?>> requestExport() => _read('exports', method: 'POST');

  @override
  Future<Map<String, Object?>> loadBlockedUsers() => _read('blocked');

  @override
  Future<Map<String, Object?>> unblockUser(String userId) =>
      _write('DELETE', 'blocked/$userId');

  @override
  Future<Map<String, Object?>> deactivateAccount() =>
      _write('POST', 'account/deactivate');

  @override
  Future<Map<String, Object?>> deleteAccount() => _write('DELETE', 'account');

  @override
  Future<Map<String, Object?>> loadStorage() => _read('storage');

  @override
  Future<Map<String, Object?>> clearCache() => _write('POST', 'storage/clear-cache');

  @override
  Future<Map<String, Object?>> submitSupportRequest(Map<String, Object?> json) =>
      _write('POST', 'support', json);
}

// Then:
SettingsApp(
  settingsDataSource: ApiSettingsDataSource(
    client,
    baseUrl: Uri.parse('https://api.example.com/v1/me/'),
    token: () => auth.accessToken,
  ),
)

Things to decide on the server side: saveSettings is called after every single change with the whole blob, so make it idempotent and last-write-wins (or debounce it in the data source); revokeSession must refuse the current device; deleteAccount should be irreversible and deactivateAccount reversible, because the screen says exactly that. If your API answers 401, refresh the token inside the data source rather than letting the screens see the failure.

When your app already has the signed-in person, pass profile: Profile(name: …, username: …, email: …) so the home card shows at once without a round trip. Saving an edit still goes through saveProfile and the card updates from the answer.

Customise the settings

A SettingsRegistry is an ordered list of SettingDefinitions. It is the single source of truth: the search reads it to build its index, each category screen reads it to draw its rows, the mapper reads it to repair stored values and UpdateSetting reads it to validate every change. Add or remove a definition and the setting appears or disappears in all four. Ids must be unique; a duplicate throws an ArgumentError when the registry is built.

Kinds of setting

ClassStored asDrawn asNeeds code in the screen?
ToggleSettingboola switch row (initial)No
ChoiceSettingthe option's String valuea radio group or, by default, a select (style: ChoiceStyle.radio for a handful); needs options and initialNo
SliderSettingthe step's int indexa stepped slider; labels names every step, initial is an indexNo
ActionSettingnothinga row that does something when tapped (destructive: true draws it as dangerous)Yes: say what the tap does
LinkSettingnothinga row with an external-link glyph; asks the host to open its SettingsLinkOnly if you add a new SettingsLink

Every definition has id, section, title, and optionally description, keywords (extra words the search matches) and group (a heading shared by consecutive rows). Toggles, choices and sliders are therefore pure data: add one and it is drawn, searched, validated, stored and reported with no new code.

Add, remove, reorder

Build a registry from the default list and pass it in. Rows appear in the order listed, so insert a new row next to its group, or it forms a second card with the same heading.

import 'package:cairn_template_settings/cairn_template_settings.dart';

SettingsRegistry buildRegistry() {
  final List<SettingDefinition> all = defaultSettingsRegistry.definitions.toList();

  // Add a toggle to the "What to notify about" group.
  final int after = all.indexWhere(
    (SettingDefinition d) => d.id == 'notifications.updates',
  );
  all.insert(
    after + 1,
    const ToggleSetting(
      id: 'notifications.reminders',
      section: SettingsSection.notifications,
      title: 'Reminders',
      description: 'A nudge when something is due',
      keywords: <String>['alarm', 'due', 'deadline'],
      group: 'What to notify about',
      initial: true,
    ),
  );

  // Add a choice to Appearance: how dense lists are.
  all.add(
    const ChoiceSetting(
      id: 'appearance.density',
      section: SettingsSection.appearance,
      title: 'List density',
      keywords: <String>['compact', 'spacing'],
      style: ChoiceStyle.radio,
      initial: 'comfortable',
      options: <ChoiceOption>[
        ChoiceOption('comfortable', 'Comfortable'),
        ChoiceOption('compact', 'Compact', 'Fits more on screen'),
      ],
    ),
  );

  // Remove: reduce motion, and the whole About category.
  all.removeWhere(
    (SettingDefinition d) =>
        d.id == SettingIds.reduceMotion || d.section == SettingsSection.about,
  );

  // Reorder: show the digest before the channel.
  final SettingDefinition digest = all.firstWhere(
    (SettingDefinition d) => d.id == 'notifications.digest',
  );
  all
    ..remove(digest)
    ..insert(
      all.indexWhere((SettingDefinition d) => d.id == 'notifications.channel'),
      digest,
    );

  return SettingsRegistry(all);
}

// Then:
SettingsApp(
  registry: buildRegistry(),
  onSettingChanged: (String id, Object? value) {
    if (id == 'appearance.density') applyDensity(value as String);
  },
)
  • Remove a whole category by removing all its definitions: it disappears from the home, the tablet list and the search. A category with no definitions is skipped, and so is a home group left empty.
  • Change an option list or a default by replacing the definition with a new const one (definitions are immutable). A stored value that is no longer offered is repaired to the default when read.
  • Search needs nothing: titles, keywords, descriptions and the section name are matched, case-insensitively, and every word of the query must match. A title match outranks a keyword match.
  • The home groups (Account, Preferences, Data and support, Session) are fixed in domain/settings/registry/home_groups.dart; rename or regroup them there (copy install).
  • Titles and summaries of the categories live on the SettingsSection enum, in domain/settings/models/settings_section.dart.
Actions and links need a line of code

The screens only know what to do for the built-in action ids (open Change password, clear the cache, sign out…). A custom ActionSetting is drawn, searched and tappable, but on most screens its tap does nothing until you add it to that view's actions map (SectionBlocks.build(actions: {'my.id': () => ...})). On About, an unknown row asks the host through onLinkTap, and SettingsLink has only terms and privacy; add a value to the enum (copy install) for a third link. If you only need a toggle, a choice or a slider, none of this applies.

Settings the screens rely on

Ids in SettingIds are special: a screen reads them directly. Everything else is drawn from its definition alone. Removing a special one is mostly safe, with these exceptions:

IdIf you remove it
SettingIds.notificationsMasterThe master switch is read as off, so every other notification row is greyed out. Remove the whole Notifications category instead.
SettingIds.textSizeThe template reads a missing step as 0 (Small, 0.9×), so text shrinks. Keep it, or with the copy install make SettingsThemeScope fall back to TextSizeSteps.defaultStep when the registry has none.
SettingIds.themeMode, SettingIds.accent, SettingIds.reduceMotionSafe: the template falls back to System, Ink and motion on. The Appearance home row loses its value.
SettingIds.editProfileThe profile card and the Edit profile screen disappear from the home.
SettingIds.faq, SettingIds.contact, SettingIds.versionEach hides its own block on the Help screen.
SettingIds.twoFactor, SettingIds.changePassword, SettingIds.sessions, SettingIds.blockedUsers, SettingIds.exportData, SettingIds.biometricSafe: the row and its sub-page entry point go.
SettingIds.signOut, SettingIds.deactivate, SettingIds.deleteAccountSafe: the row goes. Sign out is often one you want to keep and remove only deactivate and delete.

Add a section

A section is a whole screen, so a new one means a new view; this needs the copy install because SettingsSection and SettingsPage are enums. The compiler guides you: the shell and the icon function switch exhaustively, so a missing case is an error, not a blank page. Example: “Connected apps”.

  1. In domain/settings/models/settings_section.dart add connected('Connected apps', 'Calendar and contacts'), where you want it (declaration order is the search and tablet order).
  2. In core/presentation/navigation/settings_page.dart add connected('Connected apps', SettingsSection.connected),. The page's name must equal the section's name: SettingsPage.of relies on it, and it is what initialLocation: 'connected' parses.
  3. In domain/settings/registry/home_groups.dart add SettingsSection.connected to a group. A section that is in no group never shows on the home. Update the “home groups cover every section exactly once” test in test/domain_test.dart.
  4. In presentation/home/widgets/section_icons.dart add SettingsSection.connected => Icons.link,.
  5. Create presentation/connected/views/connected_view.dart (below).
  6. In presentation/shell/settings_shell.dart add SettingsPage.connected => ConnectedView(onBack: back), to the switch in _pageFor.
  7. Add its definitions to your registry with section: SettingsSection.connected.
import 'package:flutter/widgets.dart';
import 'package:flutter_bloc/flutter_bloc.dart';

class ConnectedView extends StatelessWidget {

  /// Null on a tablet, where the list is beside the page.
  final VoidCallback? onBack;

  @override

    return PageFrame(

Theme, text size, accent, motion

The template applies the person's appearance choices to itself: it wraps its content in its own Theme and MediaQuery (SettingsThemeScope), so the Appearance screen is a live preview with no wiring. It keeps your font family, fallback fonts and radius from the host's CairnTheme, and takes brightness and accent from the person's choice:

  • Light and Dark use CairnTheme.light and CairnTheme.dark.
  • System follows the host's registered CairnTheme (the one in your ThemeData extensions, as CairnTheme.materialTheme registers it) when there is one, so a host that has already resolved its own theme mode is respected. With no registered CairnTheme it follows the device brightness.
  • Accent (Ink, Ocean, Forest) replaces the primary colour and its foreground. Ink keeps the theme's own primary.
  • Text size multiplies the text scale it inherits by 0.9, 1.0, 1.15 or 1.3.
  • Reduce motion turns MediaQuery.disableAnimations on (it is OR-ed with the system setting, never turned off).

To make the rest of your app follow, listen to the two callbacks. Neither is called when the template mounts, so also read the stored values at start-up from the same place your data source keeps them.

import 'dart:convert';

import 'package:cairn_template_settings/cairn_template_settings.dart';
import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/material.dart';
import 'package:shared_preferences/shared_preferences.dart';

class AppearanceState extends ChangeNotifier {
  AppearanceState(SharedPreferences prefs) {
    // The blob PreferencesSettingsDataSource writes: { "schema": 1, "values": {...} }.
    final String? raw = prefs.getString('settings.values');
    final Object? decoded = raw == null ? null : jsonDecode(raw);
    final Object? values = decoded is Map<String, Object?> ? decoded['values'] : null;
    if (values is Map<String, Object?>) {
      for (final MapEntry<String, Object?> e in values.entries) {
        apply(e.key, e.value);
      }
    }
  }

  ThemeMode mode = ThemeMode.system;
  double textFactor = 1; // steps 0..3 -> 0.9, 1.0, 1.15, 1.3
  String accent = 'ink';
  bool reduceMotion = false;

  static const List<double> _factors = <double>[0.9, 1.0, 1.15, 1.3];

  /// Call from SettingsApp.onSettingChanged. Notifies only when it matters.
  void apply(String id, Object? value) {
    switch (id) {
      case SettingIds.themeMode:
        mode = switch (value) {
          'light' => ThemeMode.light,
          'dark' => ThemeMode.dark,
          _ => ThemeMode.system,
        };
      case SettingIds.textSize:
        textFactor = _factors[(value as int).clamp(0, _factors.length - 1)];
      case SettingIds.accent:
        accent = value as String;
      case SettingIds.reduceMotion:
        reduceMotion = value as bool;
      default:
        return;
    }
    notifyListeners();
  }
}

/// Your own accent mapping: the template's accents are internal to it.
CairnTheme hostTheme(CairnTheme base, String accent) => switch (accent) {
  'ocean' => base.copyWith(primary: const Color(0xFF1D4ED8)),
  'forest' => base.copyWith(primary: const Color(0xFF166534)),
  _ => base,
};

// In your app widget (listen to the ChangeNotifier with ListenableBuilder):
MaterialApp(
  themeMode: appearance.mode,
  theme: CairnTheme.materialTheme(hostTheme(CairnTheme.light, appearance.accent)),
  darkTheme: CairnTheme.materialTheme(hostTheme(CairnTheme.dark, appearance.accent)),
  home: Scaffold(
    body: SafeArea(
      child: SettingsApp(
        onSettingChanged: appearance.apply,
        // onThemeModeChanged is optional here: onSettingChanged already carries
        // the theme as 'light', 'dark' or 'system'.
      ),
    ),
  ),
)
Do not scale the text twice

The template multiplies the text scale it inherits by the person's text size. If you apply the same factor in MaterialApp.builder, the settings screens inherit it and the text is scaled twice (1.3 × 1.3). Apply your factor on your own screens only, or undo it around the template:

// Around SettingsApp, restore the system text scale so only the template applies the factor.
MediaQuery(
  data: MediaQuery.of(context).copyWith(
    textScaler: MediaQueryData.fromView(View.of(context)).textScaler,
  ),
  child: SettingsApp(onSettingChanged: appearance.apply),
)
  • Brand colours inside the template. Inside the settings the colours are the Cairn light and dark palettes plus the three accents, not your host theme's custom colours. To change the accents edit SettingsAppearance.accentColor and SettingsAppearance.accents in core/presentation/settings_appearance.dart and the appearance.accent options in your registry (copy install).
  • If saving fails the template restores the old value and says so, but it has already called your callbacks. Keep your app in step by making saveSettings reliable (queue and retry) rather than throwing.
  • Language and region are stored and reported (language.language, language.region, language.dateFormat, language.timeFormat, language.units); the template does not translate itself. Apply them in your app from onSettingChanged.

Sign out, deactivate, delete

The danger zone never ends a session or touches an account by itself. Each action asks for confirmation, then tells your app:

ActionConfirmationWhat the template does
Sign out“Sign out?”, onceCalls onSignOut. Signing out affects this device only. If the callback is missing, the toast says “Pass onSignOut to SettingsApp to handle this.”
Deactivate account“Deactivate your account?”, onceCalls deactivateAccount() on the data source; on ok calls onDeactivateAccount and shows “Account deactivated”. A refusal shows its error and calls nothing.
Delete accountType DELETE, then “This is the last step”Checks the word again, calls deleteAccount(); on ok calls onDeleteAccount. The row is disabled and says “Deleting...” while it runs.
SettingsApp(
  settingsDataSource: source,
  onSignOut: () async {
    await auth.signOut();               // revoke the token, clear secure storage
    await prefs.remove('settings.values'); // per-user data on a shared device
    router.go('/sign-in');
  },
  onDeactivateAccount: () {
    // The server has hidden the account already: drop the local session.
    auth.clearLocal();
    router.go('/goodbye');
  },
  onDeleteAccount: () async {
    await localDatabase.wipe();
    await prefs.clear();
    router.go('/goodbye');
  },
)

The confirmation word is deleteConfirmationPhrase in common/constants/confirmation_phrases.dart (copy install). The check is exact and case-sensitive, so autofill or a stray tap cannot delete an account; the use case verifies it too, not only the dialog. After the hook fires the template may still be on screen: navigate away in the callback.

Notification permission

Whether the operating system lets the app notify is the system's decision, not a setting, so you pass it in as notificationPermission and the screen reacts:

  • granted – the master switch works normally.
  • notDetermined – turning the master switch on first calls onRequestNotificationPermission. If it answers granted the switch turns on; any other answer leaves it off. With no callback the switch simply turns on.
  • denied – the person refused and the app cannot ask again. The screen shows “Notifications are blocked” with Open settings (onOpenSystemSettings), the master switch cannot be turned on and every row below is greyed out.

Read the status again whenever the app returns to the foreground, since the person may have changed it in the system settings:

import 'package:cairn_template_settings/cairn_template_settings.dart';
import 'package:flutter/widgets.dart';
import 'package:permission_handler/permission_handler.dart';

class SettingsPageHost extends StatefulWidget {
  const SettingsPageHost({super.key, required this.source});

  final SettingsDataSource source;

  @override
  State<SettingsPageHost> createState() => _SettingsPageHostState();
}

class _SettingsPageHostState extends State<SettingsPageHost>
    with WidgetsBindingObserver {
  NotificationPermission _permission = NotificationPermission.notDetermined;

  @override
  void initState() {
    super.initState();
    WidgetsBinding.instance.addObserver(this);
    _refresh();
  }

  @override
  void dispose() {
    WidgetsBinding.instance.removeObserver(this);
    super.dispose();
  }

  @override
  void didChangeAppLifecycleState(AppLifecycleState state) {
    if (state == AppLifecycleState.resumed) _refresh();
  }

  NotificationPermission _map(PermissionStatus status) => switch (status) {
    PermissionStatus.granted ||
    PermissionStatus.limited ||
    PermissionStatus.provisional => NotificationPermission.granted,
    // The system will not show its prompt again: the only way back is Settings.
    PermissionStatus.permanentlyDenied ||
    PermissionStatus.restricted => NotificationPermission.denied,
    // Refused once, but asking again is still possible.
    PermissionStatus.denied => NotificationPermission.notDetermined,
  };

  Future<void> _refresh() async {
    final NotificationPermission now = _map(await Permission.notification.status);
    if (mounted) setState(() => _permission = now);
  }

  @override
  Widget build(BuildContext context) {
    return SettingsApp(
      settingsDataSource: widget.source,
      notificationPermission: _permission,
      onRequestNotificationPermission: () async =>
          _map(await Permission.notification.request()),
      onOpenSystemSettings: openAppSettings,
    );
  }
}

On Android 13+ declare POST_NOTIFICATIONS in AndroidManifest.xml; on iOS enable the notification permission macro in the Podfile as permission_handler's README describes. The template only shows and stores the person's preferences (notifications.messages, notifications.digest, quiet hours…); sending, scheduling and silencing are your push backend's job, driven by onSettingChanged or by the stored blob.

About has Terms of service and Privacy policy rows. The template never opens URLs: it calls onLinkTap with a SettingsLink and you decide how (browser, in-app web view, a route). Without the callback, tapping shows a toast saying to pass onLinkTap.

Architecture

Layers

presentation ──► domain ◄── data views, cubits models, mappers, SettingsDataSource, view models registry, use cases repository implementations ▲ ▲ └──────── core (DI, hooks, widgets) ──┘ common (constants, helpers)
  • domain/ depends on nothing but Dart and common. models/ are plain objects (Profile, SettingsSnapshot, DeviceSession, the setting definitions), mappers/ convert decoded JSON, registry/ holds the SettingsRegistry and the default list, repositories/ are the interfaces and use_cases/ do one job each (LoadSettings, UpdateSetting, SearchSettings, SaveProfile, ChangePassword, RevokeSession, DeleteAccount…). Use cases throw SettingsFailure with a message written for the person.
  • data/ implements the repositories on top of SettingsDataSource and holds the in-memory demo. It is the only layer that talks to a backend.
  • presentation/ has one folder per feature (about, appearance, danger, help, home, language, notifications, privacy, profile, settings, storage) with bloc/, view_models/, views/ and widgets/, plus shell/ which composes the pages.
  • core/ is shared by every layer's consumers: the container, SettingsHooks, the navigation cubit, ViewModel and the reusable rows and frames. Features do not import each other's views; anything shared lives in core/presentation/widgets/.

Dependency injection

createSettingsLocator in core/infrastructure/di/settings_injection.dart builds a fresh GetIt.asNewInstance() for each mounted SettingsApp, never the global instance, so two copies (or a hot restart) never collide. Registration is written out by hand; there is no build_runner step. SettingsApp creates the container once, loads the settings and the profile, and calls reset() in dispose.

ScopeWhat
Singletonthe integration points: SettingsHooks, UnsavedChangesGuard, SettingsRegistry, SettingsDataSource
Lazy singletonSettingsMapper, the five repositories, and the session cubits SettingsNavigationCubit, SettingsCubit and ProfileCubit (closed by the container, never by a view model), plus SettingsNavigator
Factoryevery use case, and every view model (SearchViewModel, ProfileEditViewModel, PrivacyViewModel, ChangePasswordViewModel, SessionsViewModel, BlockedUsersViewModel, TwoFactorViewModel, StorageViewModel, SupportViewModel, AccountViewModel)

Views never touch the container. SettingsProviders exposes the session cubits with BlocProvider.value (which does not close them) and the registry, hooks, navigator and guard with RepositoryProvider.value, so a view reads them with context.read. To swap a single piece in a copy install, change its registration, for example to replace a repository:

// settings_injection.dart
..registerLazySingleton<StorageRepository>(() => MyStorageRepository(g()))

Navigation

The template deliberately does not use your app's router: it has to run unchanged inside any Flutter app. SettingsNavigationCubit holds a small stack of SettingsPages:

CallEffect
open(page)pushes a page on top (a sub-page, or a category on a phone)
select(page)makes it the only open page (the tablet list)
back()closes the top page; false when nothing was open
home()closes everything

Views call SettingsNavigator instead, which does the same but first asks “Discard changes?” when UnsavedChangesGuard.hasUnsavedChanges says an edit would be lost. On a phone the top page fills the screen with a short fade-and-slide (instant with reduced motion); on a tablet the stack's first entry is the selected category and the top is shown beside the list. SettingsShell wraps it in a PopScope so the system back goes up one page.

initialLocation opens the app on a page. It is a category name from SettingsPage – profile, appearance, notifications, privacy, language, storage, help, about, danger – or a path from category to sub-page, separated by /: privacy/changePassword, privacy/sessions, privacy/blockedUsers. Unknown names are ignored. It is read once.

View models

A view model owns what is scoped to one screen visit: it creates the feature cubit, exposes it to the view and closes it in dispose. ViewModelBuilder<T> resolves it from the container (SettingsScope.of(context)) and disposes it when the widget leaves the tree.

class SearchViewModel implements ViewModel {
  SearchViewModel(this.cubit);

  final SearchCubit cubit;

  @override
  void dispose() => cubit.close();
}

// In the view:
ViewModelBuilder<SearchViewModel>(
  builder: (BuildContext context, SearchViewModel vm) =>
      BlocProvider<SearchCubit>.value(value: vm.cubit, child: const _HomeBody()),
)

// In the container:
..registerFactory<SearchViewModel>(() => SearchViewModel(SearchCubit(g())))

Screen cubits extend SafeCubit, which ignores emit after it is closed, so a request still in flight when the screen goes cannot throw. A cubit raises a message with a Notice in its state and the view shows it as a toast with NoticeListener; each notice is distinct, so the same text twice still shows twice.

Use go_router

Mount SettingsApp as one route in your router and let initialLocation carry deep links. Use a query parameter so the page path (privacy/sessions) stays one value:

import 'package:cairn_template_settings/cairn_template_settings.dart';
import 'package:flutter/material.dart';
import 'package:go_router/go_router.dart';

GoRouter buildRouter(SettingsDataSource source) {
  return GoRouter(
    initialLocation: '/home',
    routes: <RouteBase>[
      GoRoute(path: '/home', builder: (c, s) => const HomeScreen()),
      GoRoute(path: '/sign-in', builder: (c, s) => const SignInScreen()),
      // /settings            opens the home
      // /settings?page=appearance
      // /settings?page=privacy/sessions
      GoRoute(
        path: '/settings',
        builder: (BuildContext context, GoRouterState state) {
          final String? page = state.uri.queryParameters['page'];
          return Scaffold(
            body: SafeArea(
              child: SettingsApp(
                key: ValueKey<String?>(page), // a new deep link restarts it
                settingsDataSource: source,
                initialLocation: page,
                onSignOut: () {
                  auth.signOut();
                  context.go('/sign-in');
                },
              ),
            ),
          );
        },
      ),
    ],
  );
}

// From anywhere in your app:
context.push('/settings?page=notifications');

The template's own back stack is separate from the router's: the system back goes up inside the settings first and leaves the route only from the home. Pop the route yourself from a toolbar if you want a way out on the home of a phone.

Make each page a real route

Only do this if you need the browser back button on web or a URL per page. It means editing the template (copy install). A sketch of where to cut; the template does not ship it:

  1. core/presentation/navigation/settings_navigation_cubit.dart: keep the cubit as the source of truth, but have the shell listen to it and call context.go('/settings/${page.name}') from a BlocListener.
  2. presentation/shell/settings_shell.dart: replace the AnimatedSwitcher in _OnePane with the router's child (a ShellRoute whose child routes build each view through _pageFor); the views read the session cubits by context.read and do not care how they were reached.
  3. SettingsNavigator: route its open, back and select to context.go / context.pop, keeping confirmLeave so the “Discard changes?” dialog still guards the edit form.

Everything else (use cases, mappers, cubits, tests) is untouched, which is the point of keeping navigation in one small cubit.

Without widgets, build the container directly and drive the cubits, which is how session_test.dart works:

test('a changed setting reaches the host', () async {
  final List<(String, Object?)> changes = <(String, Object?)>[];
  final GetIt locator = createSettingsLocator(
    settingsDataSource: InMemorySettingsDataSource(latency: Duration.zero),

Import createSettingsLocator, SettingsHooks and SettingsCubit from their files under package:cairn_template_settings/; they are internal to the package and not in the barrel. To test your own SettingsDataSource, run its output through SettingsMapper and the other mappers (ProfileMapper, SecurityMapper, StorageMapper, ActionResultMapper) in a unit test: a typo that fails there would fail on every user's phone.

The template's tests load Geist from the Cairn site checkout when they can find it (test/flutter_test_config.dart), so text has real metrics. Accessibility

  • Every control is named. The back control reads “Back”, the search field “Search settings”, the clear button “Clear search”; rows read their title and description, and switches announce their on or off state (a disabled one says so).
  • Headings are headings. The home title and every page title are announced as headers.
  • Targets are at least 44 × 44. Cairn's buttons are 32 to 40 px, so each is wrapped in TouchTarget, which adds an invisible margin that triggers the same action without adding a second semantic node. The input and select are Cairn's own 36 px controls; their text scales up to 1.5× inside them (ControlScale) while labels, hints and errors around them scale fully.
  • Text scaling. The text size setting multiplies the system scale, and pages scroll with the primary content reachable at 2×. Rows stack their action under their text at large sizes, and a tablet falls back from two panes to one so nothing is squeezed.
  • State is not colour alone. Errors have an icon and words and are live regions, so they are announced when they appear; the search reports “3 results” or “No results” the same way; a loading list is announced as “Loading”.
  • Focus order follows reading order (ReadingOrderTraversalPolicy): back, title, content, then actions. Cairn controls are keyboard focusable, activate on Space and Enter and show a ring on keyboard focus.
  • Reduced motion. When MediaQuery.disableAnimations is true, or the Reduce motion setting is on, page transitions are instant. Nothing in the template loops except Cairn's skeletons and spinners while something loads.
  • Destructive actions are guarded. Sign out, deactivate, clear cache, turning off two-factor and leaving unsaved edits each ask first; deleting needs a typed word and a second confirmation.

Test with TalkBack and VoiceOver on a device: the template is built to be correct by construction, but only a screen reader tells you how it sounds.

Production checklist

  1. Replace the demo data source. The in-memory one forgets everything on exit and accepts 123456 as a two-factor code. Pass a real settingsDataSource and check each failure path: a throwing read shows a retry, a refused write returns ok: false with a sentence.
  2. Stabilise setting ids before launch, and never reuse one for a different meaning. They are the storage keys.
  3. Wire the hooks you ship. onSignOut, onDeactivateAccount and onDeleteAccount must end the session and clear local data; onLinkTap must open real Terms and Privacy pages. The template shows a toast asking for a missing callback, which you do not want in production.
  4. Make the switches mean something. Biometric lock (local_auth), Wi-Fi only, auto-delete, quiet hours, language and the notification categories are only stored by the template.
  5. Replace the content. The FAQ (FaqItems), support subjects, avatar presets, licences from loadAppInfo and the version from package_info_plus.
  6. Handle notification permission on both platforms (manifest and Podfile entries), and re-read it on resume.
  7. Server-side rules. Enforce the username, password and confirmation rules on the server too; the client checks are a convenience. Refuse revoking the current session, make delete irreversible and deactivate reversible.
  8. Secrets. Never log passwords or two-factor codes in your data source. The template holds them only in memory while the form is open.
  9. Do not scale text twice if your app applies the person's text size too (Theme, text size, accent, motion).
  10. Run the checks. flutter analyze --fatal-infos --fatal-warnings and flutter test, then try the real app at 320 px, on a tablet, with 200% text, in dark mode and with a screen reader.

Troubleshooting

"No SettingsScope above this context"

You built a view or ViewModelBuilder outside SettingsApp. Mount SettingsApp (it provides the scope), or wrap your tree in a SettingsScope with a locator from createSettingsLocator().

Everything is black and white and unstyled

The host app has no CairnTheme. Use CairnTheme.materialTheme(...) or add CairnTheme.light to ThemeData.extensions.

Nothing survives a restart

The default data source is in memory. Pass a settingsDataSource that persists (see Persist the settings). Also make sure the same instance, or the same storage key, is used on every launch.

"Could not load your settings" with a retry

loadSettings, loadAppInfo or loadProfile threw. Reads must complete: add a timeout in the data source and rethrow. Try again calls them again.

My app does not follow the theme choice

The template themes itself. Your app changes only if you handle onThemeModeChanged (set MaterialApp.themeMode) and read the stored value at start-up, because the callbacks are not called on mount. With System selected, the template follows your registered CairnTheme, so the two agree.

Text is far too large inside the settings

Your app applies the text size in MaterialApp.builder and the template applies it again. See the warning under Theme, text size, accent, motion.

All the notification rows are greyed out

Either the operating system's permission is denied (the alert above the rows says so), or notifications.master is missing from your registry (a missing switch reads as off). Pass the right notificationPermission and keep the master switch.

Text got smaller after I removed a setting

You removed appearance.textSize. See Settings the screens rely on.

My new row does nothing when tapped

It is an ActionSetting or LinkSetting and the screen has no handler for its id. Add it to that view's actions map (copy install). Toggles, choices and sliders need no handler.

ArgumentError: Duplicate setting id

Two definitions in your registry share an id. Ids must be unique across all sections.

Sign out does nothing, and a toast says "Pass onSignOut"

That is the default behaviour with no callback. Pass onSignOut, onDeactivateAccount and onDeleteAccount; Terms and Privacy need onLinkTap the same way.

It opens on the home instead of the page I asked for

initialLocation must be a name from SettingsPage (appearance, privacy/sessions…); unknown names are ignored. It is read once, so give SettingsApp a new key to open another page later.

The two-pane layout does not appear on a tablet

It needs 600 px of width and text that is not very large (system scale above about 1.35 falls back to one page at a time). Check the width the widget is actually given, not the screen's.

The select's menu or a dialog is hidden or throws "No Overlay"

CairnSelect, dialogs and sheets open in the nearest Overlay. Mount the template under a MaterialApp (or WidgetsApp) so one exists.

"RenderFlex overflowed" in my tests

Flutter's test font is wide. Load your real font in test/flutter_test_config.dart and set fontFamily on the test theme.

Where do I report a bug?

Open an issue on the cairn_site repository with the Flutter and cairn_ui versions.

Migration notes

When you…Do this
Upgrade cairn_ui to a new minorBump the constraint, run flutter analyze. Components added in a minor never break this template; read the library's CHANGELOG for renames.
Add a setting that is already live elsewhereAdd a definition with a sensible initial. Existing users have no stored value, so they get the default; nothing crashes.
Remove a settingRemove its definition. Its stored value is ignored when reading and dropped on the next save. Check Settings the screens rely on first.
Rename a setting idTreat it as a removal plus an addition: users fall back to the default. To keep their choice, read the old key in your data source's loadSettings and return it under the new id once.
Remove an option from a choiceJust remove it. A stored value that is no longer offered is repaired to the default.
Change a setting's type (toggle to choice)The old value is the wrong type and is repaired to the default. Use a new id if you need to migrate it.
Change the stored shapeThe envelope is {"schema": 1, "values": {...}} (SettingsMapper.schema). Reading is forgiving, so most changes need no migration; if you do change the envelope, do it in your data source and keep returning the shape above.
Move from the copied source to the packageDelete your copy, add the dependency, change imports back to package:cairn_template_settings/…, and move your edits (usually the registry and the hooks) into your own wrapper. Anything that changed a screen, the constants or an enum stays a copy install.
Pull template updates into a copyDiff templates/settings/lib between your last sync tag and the new one; because dependencies point inwards, changes are almost always inside a single layer.
Change state managementCubits are plain streams of immutable states. Views call cubit.method() and read state, so Riverpod or Provider can replace BlocBuilder view by view.
