Jaspr store template

A server-rendered online store with first-class SEO, built with Jaspr and the Cairn design language. This guide takes you from clone it to sell with your own catalogue, brand and backend.

Overview & architecture

The template is a pure Dart package, cairn_template_jaspr_store. It is not a Flutter app and does not depend on Flutter or cairn_ui: Cairn UI is a Flutter widget library and cannot run in Jaspr. What it shares with Cairn is the design language: the OKLCH palette, radius scale, spacing grid, type scale and shadows are copied into CSS custom properties, and the components (buttons, inputs, badges, cards, alerts, accordions) match their Flutter counterparts.

Every page is rendered to HTML on a Dart server. Only three small islands ship JavaScript (a theme toggle, a cart counter and an add-to-cart enhancement), so the whole store works with JavaScript disabled: browse, search, filter, add to cart, apply a promo code, check out.

lib/
├─ app.dart                 routing, canonical redirects, Reply -> Response
├─ main.server.dart         shelf pipeline + serveApp
├─ main.client.dart         hydrates the 3 islands
├─ core/                    config (Brand, StoreConfig), Result, analytics, errors, seo/
├─ common/                  constants, utils (money, slug, escape, text)
├─ domain/<feature>/        models, repository interfaces, use cases (pure Dart)
│    catalog  cart  checkout  reviews  newsletter
├─ data/<feature>/          repository implementations
├─ presentation/            theme, components, shell, seo, islands, pages + controllers
├─ http/                    RequestInfo, Reply, middleware, sitemap/robots/manifest
├─ di/service_locator.dart  composition root (get_it)
└─ backend/                 DEMO STAND-IN: seed data, in-memory stores, cart cookie
The one rule to remember

Dependencies point inwards: presentation → domain ← data. To change where products come from you replace one repository implementation and delete lib/backend/. To change how things look you touch presentation/. Controllers return plain data (SeoData + a page component); app.dart is the only place that talks HTTP.

A request flows: RequestInfo (parsed query, cookies, bounded form body) → method and same-origin checks → path hygiene (301) → controller → Reply (page, redirect, raw, not-found) → render Document(head: buildHead(seo), body: SiteShell(page)) → response with status, Cache-Control, ETag, Vary and Set-Cookie.

Install & run

cd templates/jaspr_store
dart pub get
dart run build_runner build      # generates lib/main.*.options.dart (gitignored)
jaspr serve                      # http://localhost:8080, hot reload

Production build and run:

jaspr build --dart-define=APP_ENV=production --dart-define=SITE_URL=https://shop.example
PORT=8080 SITE_URL=https://shop.example CART_SECRET=$(openssl rand -hex 32) ./build/jaspr/app

build/jaspr/app is an AOT-compiled server; build/jaspr/web holds the island JavaScript and your static files and must sit next to it.

Only one build daemon per directory

jaspr serve and jaspr build cannot run at the same time ("Incompatible options with current running build daemon"). Stop the dev server first.

Try the demo: add something to the cart, apply CAIRN10 for 10% off, then check out with any valid-looking address (a US ZIP is five digits). The checkout never asks for a card.

Add a product

  1. Generate its images (next section) and put them in web/images/products/.
  2. Append a Product(...) to seedProducts() with a unique id, slug, sku, gtin and variant ids.
  3. Run dart test test/domain/catalog_test.dart. It fails on duplicate ids/slugs/SKUs, a bad GTIN check digit, an unknown category, or an image file missing on disk.
  4. Restart the server. The product appears in listings, search, the sitemap (with lastmod and an image entry) and gets Product JSON-LD automatically.

Categories

Add a Category(slug, name, headline, description, image) to seedCategories(). It gets an indexable landing page at /categories/<slug> with its own title, description and BreadcrumbList, a navigation entry, a home tile and a sitemap entry. Write a distinct description: it becomes the meta description, and a test asserts that every page's title and description are unique.

Images and srcset generation

ProductImage(base: 'x', alt: ...) expects these files in web/images/products/:

x-350.webp   x-700.webp   x.jpg (700 px fallback)

The template renders <picture><source type="image/webp" srcset="x-350.webp 350w, x-700.webp 700w" sizes="..."><img src="x.jpg" width="700" height="700" alt="..." loading="lazy" decoding="async">. The intrinsic width/height reserve the box so nothing shifts when the image arrives; CSS (aspect-ratio: 1, object-fit: cover) crops every photo to a consistent square.

# tool/make_images.py  (needs: pip install Pillow)
import sys
from PIL import Image

def square(im):
    w, h = im.size; s = min(w, h)
    l, t = (w - s) // 2, (h - s) // 2
    return im.crop((l, t, l + s, t + s))

src, name = sys.argv[1], sys.argv[2]
im = square(Image.open(src).convert('RGB'))
out = 'web/images/products/' + name
for w in (350, 700):
    im.resize((w, w), Image.LANCZOS).save(f'{out}-{w}.webp', 'WEBP', quality=70, method=6)
im.resize((700, 700), Image.LANCZOS).save(f'{out}.jpg', 'JPEG', quality=74, optimize=True, progressive=True)
python tool/make_images.py ~/Downloads/shirt.jpg linen-shirt

Different sizes? Change ProductImage.widths, width and height. Always write real alt text: it is read aloud, shown when the image fails, and used for og:image:alt. Photo credits for the bundled images are in NOTICE.md. Image files are cached for a week, so rename a file when you change it.

Update tests when you rebrand

The tests assert on "Northgate Goods", the seed products and https://shop.example. A global rename in test/ plus re-running dart test is the quickest way to confirm nothing else hard-codes the old brand.

Verify

  1. Raw HTML: curl -s https://your.site/products/stride-knit-sneaker | grep -A1 ld+json. If it is there, a crawler sees it.
  2. The bundled audit: dart run tool/seo_audit.dart https://your.site crawls your sitemap and fails on missing or duplicate titles, canonicals, h1s, relative OG URLs, invalid JSON-LD, images without alt/size, unlabelled controls or broken links. Use it in CI against a staging deployment.
  3. Rich results: paste a product URL into Google's Rich Results Test (search.google.com/test/rich-results). Expect "Product snippets" and "Merchant listings" with no errors.
  4. Schema validator: validator.schema.org accepts a URL or pasted JSON-LD and checks property types.
  5. Lighthouse: Chrome DevTools → Lighthouse → mobile. Expect near-100 for SEO and Accessibility; LCP is the preloaded first image.
  6. Search Console: submit /sitemap.xml; inspect a few URLs ("Test live URL" shows the rendered HTML).
  7. Open Graph preview: the Facebook Sharing Debugger, LinkedIn Post Inspector, or just paste the URL into Slack or iMessage. The tags are in the first response, so they unfurl without JavaScript.

Sitemap and robots

/sitemap.xml is generated per request: home, /products, every category (with the newest product's date as lastmod), every product (lastmod = updatedAt, plus image entries), and /about. Update a product's updatedAt when its content changes, as it is the signal crawlers use. /robots.txt allows everything except /cart, /checkout, /newsletter, /search and ?q= / ?sort= URLs, and points at the sitemap using SITE_URL.

Canonical rules

  • One URL per state: /products?page=1, ?sort=featured, ?q= and trailing slashes answer 301 to the canonical form. /products?category=audio → /categories/audio.
  • Paginated pages 2+ are self-canonical and indexable with rel=prev/next (otherwise the products on them would be unreachable for crawlers).
  • Sorted pages canonicalise to the unsorted page (no noindex, so there is no conflicting signal).
  • Search results are noindex, follow and disallowed in robots.txt.
  • Unknown slug, malformed slug or a page past the end: real 404. A renamed product: add the old slug to previousSlugs and it 301s.

Example: Postgres catalogue

-- schema (sketch)
create table products (
  id text primary key, slug text unique not null, name text not null, brand text,
  category_slug text not null, summary text, description jsonb, price_cents int not null,
  compare_at_cents int, sku text unique, gtin text, images jsonb, tags text[],
  featured bool default false, created_at timestamptz, updated_at timestamptz
);
create table variants (
  id text primary key, product_id text references products(id), label text,
  sku text unique, stock int not null check (stock >= 0), price_cents int
);
create table product_slugs (old_slug text primary key, product_id text references products(id));
// lib/data/catalog/postgres_catalog_repository.dart   (package:postgres)
class PostgresCatalogRepository implements CatalogRepository {
  PostgresCatalogRepository(this._db);
  final Connection _db;

  @override
  Future<Product?> productBySlug(String slug) async {
    final rows = await _db.execute(
      Sql.named('select * from products where slug = @slug'), parameters: {'slug': slug});
    if (rows.isEmpty) return null;
    return _hydrate(rows.first.toColumnMap());   // join variants + ratings
  }

  @override
  Future<bool> reserveStock(Map<String, int> qty) => _db.runTx((tx) async {
    for (final e in qty.entries) {
      final r = await tx.execute(
        Sql.named('update variants set stock = stock - @n where id = @id and stock >= @n'),
        parameters: {'id': e.key, 'n': e.value});
      if (r.affectedRows == 0) { tx.cancelTransaction(); return false; }  // roll back everything
    }
    return true;
  });
  // allProducts, productById, productByPreviousSlug (join product_slugs), categories ...
}

Keep the contract: reserveStock is all-or-nothing and must not oversell (the stock >= n guard in the UPDATE is what makes it safe under concurrency; test/domain/checkout_test.dart has the oversell scenario to port to your integration tests). Push filtering/sorting into SQL by implementing a queryProducts on the repository and keeping the same ProductListing result, or keep the in-memory applyQuery for catalogues of a few thousand rows and cache allProducts() for a minute.

REST: implement the same interfaces with package:http against your API, mapping JSON into the domain models in one mapper file. Firestore: store products as documents keyed by id; use a transaction for reserveStock; the sitemap and listing need all products, so cache them in memory with a short TTL.

Payments: Stripe Checkout and a webhook

The demo checkout never takes money

It records an order and says so on every screen. To sell, replace the "place order" step with a redirect to a hosted payment page, and only mark an order paid from a verified webhook, never from the browser redirect.

  1. POST /checkout validates the form and re-prices the cart (unchanged), saves an order with status pending, then creates a Stripe Checkout Session and redirects with 303 to its URL.
  2. Stripe collects the card on its own domain (your server never sees card data, so PCI scope stays minimal).
  3. Stripe calls POST /webhooks/stripe; you verify the signature and mark the order paid.
  4. The success URL (/checkout/confirmation/:id) shows the order, with "payment processing" until the webhook arrives.
// create the session (server only; STRIPE_SECRET_KEY from the environment)
final response = await http.post(
  Uri.https('api.stripe.com', '/v1/checkout/sessions'),
  headers: {'Authorization': 'Bearer $stripeSecret'},
  body: {
    'mode': 'payment',
    'success_url': '${config.origin}/checkout/confirmation/${order.id}',
    'cancel_url': '${config.origin}/cart',
    'client_reference_id': order.id,
    'customer_email': order.email,
    for (var i = 0; i < order.lines.length; i++) ...{
      'line_items[$i][quantity]': '${order.lines[i].quantity}',
      'line_items[$i][price_data][currency]': config.currency.toLowerCase(),
      'line_items[$i][price_data][unit_amount]': '${order.lines[i].unitCents}',
      'line_items[$i][price_data][product_data][name]': order.lines[i].name,
    },
  },
);
final url = (jsonDecode(response.body) as Map)['url'] as String;
return RedirectReply(url);   // 303
// webhook: verify  Stripe-Signature: t=...,v1=...
bool verifyStripe(String payload, String header, String secret, {Duration tolerance = const Duration(minutes: 5)}) {
  final parts = {for (final p in header.split(',')) p.split('=')[0]: p.split('=')[1]};
  final t = int.parse(parts['t']!);
  final age = DateTime.now().difference(DateTime.fromMillisecondsSinceEpoch(t * 1000));
  if (age.abs() > tolerance) return false;
  final mac = Hmac(sha256, utf8.encode(secret)).convert(utf8.encode('$t.$payload'));
  return constantTimeEquals(mac.toString(), parts['v1']!);
}
// on event.type == 'checkout.session.completed': orders.markPaid(session.client_reference_id)
// Make the handler idempotent (Stripe retries): ignore an order that is already paid.

Mount the webhook outside the same-origin guard (Stripe is a server, not a browser) by routing /webhooks/stripe in app.dart before the isSameOriginPost check, read the raw body, and exclude it from CSRF. Reserve stock when the order is created and release it when a session expires (checkout.session.expired). Amounts must come from PriceCart on the server, never from a form field.

Cart cookie design & security

The browser holds a single cookie, cart (__Host-cart over https), containing <id>.<tag>: a 128-bit random id and a 128-bit truncated HMAC-SHA256 tag. The cart itself (variant ids and quantities) lives on the server keyed by the SHA-256 of the id. No prices are stored anywhere a client can reach: they are recomputed from the catalogue on every read, so tampering cannot change what is charged.

ChoiceReason
Server-keyed cart, not a signed client cartNo 4 KB limit, expirable, inspectable, never trusts a client-held price, easy to merge or clear.
Sign the idForged or junk ids are rejected before any lookup; rotating CART_SECRET invalidates all carts.
HttpOnlyScript (including a compromised dependency) cannot read the cookie.
SameSite=Lax + Origin / Sec-Fetch-Site check on POSTsCross-site form posts neither carry the cookie nor pass the guard.
Secure + __Host- prefix on httpsNo overwriting by sibling subdomains; no plain-text transport.
Hash-keyed, bounded, TTL storeA leaked dump has no usable ids; memory is capped (10,000 carts, 14 days, least-recent eviction).
Cart created on first successful add onlyCrawlers and prefetchers cannot allocate server memory.
Order ids are 96-bit randomConfirmation URLs are unguessable; the page is noindex and no-store.

Set CART_SECRET to a stable 32+ character random value in production. Without it a random per-process secret is used (safe, but carts reset on restart). If you add accounts, merge the anonymous cart into the account cart on login and rotate the id.

CDN caching

Catalogue pages send public, max-age=60, s-maxage=300, stale-while-revalidate=86400, a weak ETag and Vary: Cookie, Accept-Encoding. They are identical for every visitor (the cart count is an island), so a CDN may cache them. The HTML varies only by the theme cookie: set the cache key to include only that cookie, and never cache /cart, /checkout, /newsletter or /cart/* (they send no-store). Purge product URLs when you change a product, or accept the 5 minute staleness. Terminate TLS at the CDN or platform; the app emits HSTS when SITE_URL is https.

Testing

dart format --output=none --set-exit-if-changed .

The tests use a small in-process "browser" (test/support/harness.dart) with a cookie jar and an HTML parser, so a flow test reads like a visitor: browser.post('/cart/add', {...}), follow the 303, parse the cart. Domain tests are plain Dart. Component tests render a component to an HTML fragment. Test the built binary too

Handler-level tests cannot see what Jaspr's own server layer does before your code runs. (For example, unknown file extensions are answered 404 before the app: /robots.txt was a 404 in production until allowedPathSuffixes was configured in main.server.dart.) Run dart run tool/seo_audit.dart http://localhost:8080 against build/jaspr/app in CI.

Migration

Upgrading Jaspr

  1. Bump jaspr, jaspr_builder, jaspr_test together, and the global jaspr_cli to the same minor.
  2. Check build_web_compilers: it is pinned (>=4.8.0 <4.8.1) because later versions need a newer Dart than 3.12. Raise the pin only when your SDK allows it.
  3. dart run build_runner build, then dart analyze --fatal-infos and dart test. Deprecations show up as analyzer infos (for example fragment() became Component.fragment()).
  4. Run the production build and tool/seo_audit.dart against it.

Moving from Flutter web

  • Keep the domain layer. Models, use cases and repository interfaces here are plain Dart; a Flutter app's equivalents move across with imports changed. Delete anything that imports package:flutter.
  • Translate widgets to elements. Column/Row become div with flex CSS; Text becomes p/span/h1; ElevatedButton becomes a.btn or button.btn; TextField becomes a labelled input. The component names in presentation/components mirror the Cairn widgets.
  • Routes become server routes. There is no client router: add a case to _route in app.dart, a controller method that returns a Reply, and a page component.
  • State: Bloc/Provider state becomes request-scoped data (the server resolves it before render) plus small StatefulComponent islands for genuinely interactive bits.
  • Forms: prefer a real <form method="post"> and a 303 redirect, and enhance with an island only for instant feedback.

Troubleshooting & FAQ

Undefined name 'defaultServerOptions'

The generated lib/main.server.options.dart is missing. Run dart run build_runner build before analyzing or testing.

"Incompatible options with current running build daemon"

A jaspr serve is still running. Stop it before jaspr build or build_runner.

/robots.txt or another dotted path is 404 in production

Jaspr only passes extension-less paths and html, htm, xml to your handler. Add the suffix to allowedPathSuffixes in main.server.dart (already done for txt and webmanifest).

The skip link jumps to the home page

A <base href="/"> tag is present. Document(base: null) removes it (already set in app.dart).

The cart badge never shows a number

It is filled in by the CartLink island from GET /cart/summary. Check that main.client.dart.js loads (CSP script-src 'self') and that the cart cookie is being sent (https sites need Secure cookies: serve over https or use http://localhost).

Add to cart redirects instead of updating in place

That is the no-JavaScript path working. If it happens with JavaScript enabled, the island did not hydrate: open the console and look for a blocked script or a failed main.client.dart.js.

Google shows the wrong price or no rich result

Run the Rich Results Test on the live URL. Common causes: SITE_URL still localhost (absolute URLs point nowhere), a missing GTIN, or priceValidUntil in the past (recomputed on every render in this template).

Why does a search page return noindex and also appear in robots.txt?

Belt and braces: the disallow stops crawling of the unbounded search space; the meta tag covers any such URL that is linked from elsewhere. The trade-off (a disallowed URL's noindex is not seen) is documented in the README.

Can I statically export it?

The catalogue pages are pure functions of the catalogue, so they can be pre-rendered, but cart, checkout, newsletter, /cart/summary, 304s and real status codes need the server. This template is tested in server mode only.

Where do I report a bug?

Open an issue on the cairn_site repository with the Dart and Jaspr versions.
