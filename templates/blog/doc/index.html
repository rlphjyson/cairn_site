Blog template

A production-ready blog for Flutter, built only from cairn_ui. This page is the whole manual: how to install it, mount it, put your own content in it, connect a real backend and keep it up to date. It is one file with no external requests, so it works offline and prints cleanly.

Overview

The template is a standalone package, cairn_template_blog, with one entry widget, BlogApp. It has four features:

  • Posts (home). A sticky navbar with live search, a featured post, category chips, a grid of post cards (six per page) with CairnPagination, and loading, empty and error states.
  • Post detail. Breadcrumb, headline, author line, cover, a body rendered from content blocks (heading, paragraph, quote, bullet list, code, image with caption), tags, a copy-link button that toasts, an author card, related posts and a way back.
  • Authors (About). The people who write, with a bio and post count each.
  • Newsletter. A validated sign-up form on the home page and in the footer, with submitting, success and error states.

It is responsive to its own width (one column under 640 logical pixels, two under 1024, three above), works in light and dark through CairnTheme, and uses no hard-coded colours except overlays on photos.

How it is organised

lib/
  blog_app.dart                 BlogApp, the entry widget
  cairn_template_blog.dart      barrel
  core/
    infrastructure/di/          blog_injection.dart: the get_it container
    presentation/               navigation cubit, view model, shared widgets
  common/                       constants (brand, config, package name), utils
  data/<feature>/
    remote/                     data source interface + InMemory stand-in
    repositories/               implementations of the domain interfaces
  domain/<feature>/
    models/ mappers/ repositories/ use_cases/
  presentation/
    feed/ post/ authors/ newsletter/   bloc, view_models, views, widgets
    shell/                      providers, navbar, footer, frame

Dependencies point inwards: presentation depends on domain, data depends on domain, and domain depends on nothing but Dart. Views never touch the container; screen-scoped cubits come from a ViewModelBuilder, session cubits from context.read. There is no code generation.

Cairn components used

CairnNavbar, CairnInput, CairnButton, CairnBadge, CairnAvatar, CairnHero, CairnCard, CairnPagination, CairnBreadcrumb, CairnSeparator, CairnSkeleton, CairnSpinner, CairnEmpty, CairnAlert, CairnLink, CairnStat, CairnToaster and CairnToast, plus Cairn tokens (CairnTheme, CairnSpacing, CairnTypography, CairnMotion, CairnShadows) and a few Material Icon glyphs Cairn does not have.

Install

Option A: as a package

Keep the folder where it is, or copy templates/blog anywhere, and depend on it by path or git. The images travel with the package.

pubspec.yaml 
dependencies:
  cairn_ui: ^0.2.0
  cairn_template_blog:
    path: ../templates/blog
  # or from git:
  # cairn_template_blog:
  #   git:
  #     url: https://github.com/your-org/your-repo.git
  #     path: templates/blog

Run flutter pub get. Nothing else to declare: the package lists assets/images/ itself, and images resolve through BlogPackage.name.

Option B: copy the source into your app

Choose this if you want to edit the template freely, for example to use go_router (see below).

  1. Copy lib/ into your app, for example to lib/blog/, and assets/images/ to your app's assets/images/. Rewrite the package imports (package:cairn_template_blog/...) to your app's package name if you use any.
  2. Add the dependencies from the table above to your pubspec.yaml.
  3. Declare the images: 
    flutter:
  assets:
    - assets/images/
  4. Tell the template the images belong to your app, not to a package: lib/blog/common/constants/blog_package.dart 
    abstract final class BlogPackage {
  static const String? name = null;
}
  5. Mount BlogApp as shown next.
Why the package name matters

With name = 'cairn_template_blog' an asset path such as assets/images/cover-laptop-code.jpg is loaded as packages/cairn_template_blog/assets/images/.... If you copy the files into your app and leave that value, every bundled photograph shows the grey fallback box.

Mount it

The template reads colours, radii and type from CairnTheme, so the host app must provide one. BlogApp fills the space its parent gives it and measures that space, not the screen, so it also works inside a panel. It brings its own CairnToaster and Material, and creates (and disposes) its own GetIt container, so two copies never share state.

lib/main.dart 
import 'package:cairn_template_blog/cairn_template_blog.dart';
import 'package:cairn_ui/cairn_ui.dart';
import 'package:flutter/material.dart';

void main() => runApp(const MyBlog());

class MyBlog extends StatelessWidget {
  const MyBlog({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'Fieldnotes',
      debugShowCheckedModeBanner: false,
      theme: CairnTheme.materialTheme(CairnTheme.light),
      darkTheme: CairnTheme.materialTheme(CairnTheme.dark),
      themeMode: ThemeMode.system,
      home: const Scaffold(body: BlogApp()),
    );
  }
}

BlogApp accepts three optional data sources, used in the backend section below: postsDataSource, authorsDataSource and newsletterDataSource.

Run it

flutter run -d chrome (or any device). Try the search box, the category chips, page 2, an article, "Copy link", the About page and the footer form. An address ending in @error.test shows the form's error state.

Update the content

All sample content lives in one file, lib/data/posts/remote/blog_seed.dart, as the decoded JSON a CMS would return. It is read by two small classes, InMemoryPostsRemoteDataSource and InMemoryAuthorsRemoteDataSource. To use your own content you either edit that file or, better, replace those classes (see "Connect a real backend"). The shapes below are the contract either way.

Add a post

  1. Add the cover image to assets/images/ (or use a URL).
  2. Append an object to seedPosts in blog_seed.dart: 
    <String, Object?>{
  'id': 'shipping-our-first-release',
  'title': 'Shipping our first release',
  'excerpt': 'What we cut, what we kept and what we would do again.',
  'category': 'Product',
  'tags': <String>['release', 'planning'],
  'author': 'priya-nair',
  'publishedAt': '2026-10-02T09:00:00',
  'cover': 'assets/images/my-cover.jpg',
  'coverAlt': 'A team celebrating around a laptop',
  'body': <Map<String, Object?>>[
    {'type': 'paragraph', 'text': 'We shipped on a Tuesday.'},
    {'type': 'heading', 'level': 2, 'text': 'What we cut'},
    {'type': 'list', 'items': <String>['Dark launch', 'Export']},
    {'type': 'code', 'language': 'bash', 'code': 'flutter build web'},
  ],
},
  3. Hot reload. It appears first in the list (or in the hero, if you add 'featured': true), the category chips update by themselves, and the page count follows.

Add an author

  1. Add a square portrait to assets/images/.
  2. Append to seedAuthors: 
    <String, Object?>{
  'id': 'sam-okafor',
  'name': 'Sam Okafor',
  'role': 'Designer',
  'bio': 'Sam designs the things you click.',
  'avatar': 'assets/images/author-sam.jpg',
},
  3. Refer to sam-okafor from a post's author field. The About page lists every author, including ones with no posts yet ("0 posts").

Images

  • Cover: landscape, 1000 px wide or more (1600 px for the featured post). Cards crop to 16:10, the desktop hero to 4:3 and the article to 2:1, always centred, so keep the subject near the middle.
  • Avatar: square, crop to the face yourself; it is shown as a circle.
  • Budget: the sample set is about 1.6 MB. Prefer JPEG at quality 80 or WebP, and avoid shipping originals.
  • Licensing: the bundled photographs are Pexels samples (see NOTICE.md). Replace them before you publish.
  • Any cover, avatar or src starting with http:// or https:// is fetched over the network instead of read from assets. On Flutter web the image host must allow CORS.

Categories and tags

There is no category table. The chips are the distinct category values of the loaded posts, ordered by how many posts each has and then alphabetically. Rename a category by editing the posts. Tags are free-form and appear as #tag links under an article; clicking one searches for it.

Branding and theming

final CairnTheme light = CairnTheme.light.copyWith(

  primaryForeground: const Color(0xFFFFFFFF),

  fontFamily: 'Inter',
  fontFamilyFallback: const <String>['system-ui', 'sans-serif'],
);
final CairnTheme dark = CairnTheme.dark.copyWith(
  primary: const Color(0xFF2DD4BF),
  primaryForeground: const Color(0xFF042F2E),
  radius: 12,

MaterialApp(
  theme: CairnTheme.materialTheme(light),
  darkTheme: CairnTheme.materialTheme(dark),

Logo, name and copy

The logo is a rounded square with a single letter, drawn in blog_navbar.dart (_Brand). Change BlogBrand.name and BlogBrand.mark and it follows. For a real logo, replace the Container in _Brand with an Image.asset or an SvgPicture.

Nav links and footer links

The navbar has two links (Blog and About) in BlogNavbar; the footer's "Explore" and "Topics" columns are in blog_footer.dart. Topics come from the categories, so they stay in step with your content.

Connect a real backend

The data layer is built so that this is the only change you make. Three interfaces return decoded JSON, and the mappers turn it into models:

InterfaceMethodReturns
PostsRemoteDataSourcefetchPosts()Future<List<Map<String, Object?>>>, shaped like the post table above
AuthorsRemoteDataSourcefetchAuthors()the same for authors
NewsletterRemoteDataSourcesubscribe(String email){"status": "subscribed"}, {"status": "already_subscribed"} or {"error": "message"}

The in-memory classes are the only implementations the template ships. Throwing from a data source makes the screen show its error state with a retry button.

A REST implementation

Add the http package (flutter pub add http), then:

lib/cms/rest_data_sources.dart 
import 'dart:convert';

import 'package:cairn_template_blog/cairn_template_blog.dart';
import 'package:http/http.dart' as http;

/// Reads posts and authors from a JSON API:
///   GET {base}/posts    -> [ {id, title, ...}, ... ]
///   GET {base}/authors  -> [ {id, name, ...}, ... ]
class RestPostsDataSource implements PostsRemoteDataSource {
  RestPostsDataSource(this._client, this._base);

  final http.Client _client;
  final Uri _base;

  @override
  Future<List<Map<String, Object?>>> fetchPosts() =>
      _getList(_client, _base.resolve('posts'));
}

class RestAuthorsDataSource implements AuthorsRemoteDataSource {
  RestAuthorsDataSource(this._client, this._base);

  final http.Client _client;
  final Uri _base;

  @override
  Future<List<Map<String, Object?>>> fetchAuthors() =>
      _getList(_client, _base.resolve('authors'));
}

class RestNewsletterDataSource implements NewsletterRemoteDataSource {
  RestNewsletterDataSource(this._client, this._base);

  final http.Client _client;
  final Uri _base;

  @override
  Future<Map<String, Object?>> subscribe(String email) async {
    final http.Response response = await _client.post(
      _base.resolve('subscribers'),
      headers: const <String, String>{'content-type': 'application/json'},
      body: jsonEncode(<String, String>{'email': email}),
    );
    if (response.statusCode == 409) {
      return const <String, Object?>{'status': 'already_subscribed'};
    }
    if (response.statusCode >= 400) {
      return const <String, Object?>{
        'error': 'We could not save your subscription. Try again soon.',
      };
    }
    return const <String, Object?>{'status': 'subscribed'};
  }
}

Future<List<Map<String, Object?>>> _getList(http.Client client, Uri url) async {
  final http.Response response = await client.get(url);
  if (response.statusCode != 200) {
    throw http.ClientException('HTTP ${response.statusCode}', url);
  }
  final List<Object?> decoded = jsonDecode(response.body) as List<Object?>;
  return <Map<String, Object?>>[
    for (final Object? item in decoded)
      (item! as Map<Object?, Object?>).cast<String, Object?>(),
  ];
}

Register it

Easy way: pass the data sources to the widget. No template file changes.

final http.Client client = http.Client();
final Uri api = Uri.parse('https://api.example.com/v1/');

BlogApp(
  postsDataSource: RestPostsDataSource(client, api),
  authorsDataSource: RestAuthorsDataSource(client, api),
  newsletterDataSource: RestNewsletterDataSource(client, api),
)

In the container: if you copied the source, replace the three registrations at the top of createBlogLocator in lib/core/infrastructure/di/blog_injection.dart:

g
  ..registerLazySingleton<PostsRemoteDataSource>(
    () => RestPostsDataSource(http.Client(), Uri.parse('https://api.example.com/v1/')),
  )
  ..registerLazySingleton<AuthorsRemoteDataSource>(
    () => RestAuthorsDataSource(http.Client(), Uri.parse('https://api.example.com/v1/')),
  )
  ..registerLazySingleton<NewsletterRemoteDataSource>(
    () => RestNewsletterDataSource(http.Client(), Uri.parse('https://api.example.com/v1/')),
  );

If your JSON has a different shape

Prefer to adapt inside the data source: fetch, then rename keys so the result matches the tables above. If the shape is very different, extend PostMapper (lib/domain/posts/mappers/post_mapper.dart); it is the single place JSON becomes a Post, and its tests (test/domain_test.dart) show what it guarantees. Rich text from a CMS (Markdown, Portable Text, HTML) should be converted to the block list in the data source or in a mapper; the renderer only knows blocks.

Firebase (Cloud Firestore)

import 'package:cloud_firestore/cloud_firestore.dart';

class FirestorePostsDataSource implements PostsRemoteDataSource {
  FirestorePostsDataSource(this._db);

  final FirebaseFirestore _db;

  @override
  Future<List<Map<String, Object?>>> fetchPosts() async {
    final QuerySnapshot<Map<String, dynamic>> snap =
        await _db.collection('posts').orderBy('publishedAt', descending: true).get();
    return <Map<String, Object?>>[
      for (final QueryDocumentSnapshot<Map<String, dynamic>> doc in snap.docs)
        <String, Object?>{
          ...doc.data(),
          'id': doc.id,
          // The mapper expects an ISO string, Firestore stores a Timestamp.
          'publishedAt': (doc['publishedAt'] as Timestamp)
              .toDate()
              .toIso8601String(),
        },
    ];
  }
}

Write the authors source the same way over an authors collection. Store the body as an array of maps using the block shapes above.

Server-side search and paging

The template loads every post and filters and pages in memory (QueryPosts), which is right up to a few hundred posts. For more, replace QueryPosts and PostsFeedCubit with versions that call your API per query. The views only read PostsFeedState, so they do not change.

Use go_router instead of the built-in navigation

The template navigates with BlogNavigationCubit (home, post(id), about) so that it runs inside any app without a router. For deep links and real URLs (/post/my-first-post) swap it for go_router. Do this on the copied source (Option B). The views stay as they are; you change three things.

  1. Make the shell take a child. In presentation/shell/blog_shell.dart give BlogShell a child and delete the private _Page widget: 
    class BlogShell extends StatefulWidget {
  const BlogShell({super.key, required this.child});

  final Widget child;
  // ...

// in the Column that held `const _Page()`:
children: <Widget>[
  widget.child,
  BlogFooter(onBackToTop: () => _toTop(animate: true)),
],
    Replace the BlocListener<BlogNavigationCubit, BlogRoute> that scrolls to the top with a call to _toTop() from a RouterDelegate listener or from each route's pageBuilder.
  2. Keep the cubit's API, change what it does. The views call openHome, openPost, openAbout and back on the cubit. Subclass it so those calls drive the router: 
    import 'package:go_router/go_router.dart';

class RouterNavigationCubit extends BlogNavigationCubit {
  RouterNavigationCubit(this.router);

  final GoRouter router;

  @override
  void openHome() => router.go('/');

  @override
  void openPost(String id) => router.push('/post/$id');

  @override
  void openAbout() => router.push('/about');

  @override
  void back() => router.canPop() ? router.pop() : router.go('/');
}
    Register it in blog_injection.dart in place of BlogNavigationCubit.new, passing the router (create the router first and hand it to createBlogLocator). Because the cubit's state no longer changes, make the navbar's active link read the location instead: in _NavLink usage in blog_navbar.dart, compute active from GoRouterState.of(context).uri.path.
  3. Declare the routes and mount with MaterialApp.router. 
    final GetIt locator = createBlogLocator();
late final GoRouter router = GoRouter(
  routes: <RouteBase>[
    ShellRoute(
      builder: (BuildContext c, GoRouterState s, Widget child) =>
          BlogShell(child: child),
      routes: <RouteBase>[
        GoRoute(path: '/', builder: (c, s) => const FeedView()),
        GoRoute(
          path: '/post/:id',
          builder: (c, s) => PostDetailView(
            key: ValueKey<String>(s.pathParameters['id']!),
            postId: s.pathParameters['id']!,
          ),
        ),
        GoRoute(path: '/about', builder: (c, s) => const AboutView()),
      ],
    ),
  ],
);

MaterialApp.router(
  routerConfig: router,
  theme: CairnTheme.materialTheme(CairnTheme.light),
  darkTheme: CairnTheme.materialTheme(CairnTheme.dark),
  builder: (BuildContext context, Widget? child) => BlogScope(
    locator: locator,
    child: BlogProviders(
      locator: locator,
      child: CairnToaster(child: child ?? const SizedBox.shrink()),
    ),
  ),
);
Why the key on the post route

PostDetailView loads its post once when it is created. Keying it by id makes a related-post click create a fresh view model instead of reusing the old one.

With path URLs, call usePathUrlStrategy() from flutter_web_plugins before runApp (see the deployment section).

SEO and deployment notes for Flutter web

Build

flutter build web --release --tree-shake-icons
# serving from a sub-path such as https://example.com/blog/
flutter build web --release --base-href /blog/
  • Base href. --base-href must start and end with a slash and match where you serve the app. Without it, assets 404 on any non-root path. You can also edit <base href="/"> in web/index.html by hand.
  • Path URLs and the 404 fallback. With usePathUrlStrategy() (or go_router without the hash), a visitor can open /post/my-post directly, and the server must answer with index.html for any path that is not a file. Examples: Firebase Hosting "rewrites": [{"source": "**", "destination": "/index.html"}]; Netlify /* /index.html 200 in _redirects; nginx try_files $uri /index.html;; GitHub Pages: copy index.html to 404.html.
  • Meta tags. Flutter renders to a canvas, so crawlers and link-preview bots see only what is in web/index.html. Put a good <title>, <meta name="description">, og:title, og:description, og:image and a favicon there. They apply to every URL.
  • Per-post titles. Set the tab title when an article opens with SystemChrome.setApplicationSwitcherDescription(ApplicationSwitcherDescription(label: post.title, primaryColor: 0xFF000000)). This changes document.title; it does not change what crawlers see.
  • Per-post previews and indexing. If search traffic or link previews matter, Flutter alone is not enough. Generate a small static HTML file per post at build time (title, description, Open Graph tags, a link into the app, and the text), publish a sitemap.xml, and have the server serve those files to bots. A static-site generator or an edge function that injects meta tags into index.html both work.
  • Caching. Serve main.dart.js and assets with long cache lifetimes (they are fingerprinted by the service worker manifest) and index.html with no-cache.
  • Remote images. If covers are URLs on another host, that host must send CORS headers for the canvas renderer to draw them.

Writing your own widget tests

  • Pass a fake data source to BlogApp to control the content or force an error (BlogApp(postsDataSource: FailingPosts())).
  • Set the window with tester.view.physicalSize and devicePixelRatio = 1.
  • Do not use pumpAndSettle. Cairn's skeletons and spinners animate forever, so it never settles. Pump in small steps, await tester.pump(const Duration(milliseconds: 100)) a few times. An AnimatedSwitcher's outgoing child stays mounted until a couple of pumps after the page changes.
  • Use a real font in layout tests. flutter test renders every glyph as the same wide box unless a font is registered, which makes a row that fits for real overflow in the test. test/flutter_test_config.dart loads Geist when it can find it; pass fontFamily: 'Geist' on your CairnTheme too.
  • Scroll before tapping with await tester.ensureVisible(finder); everything below the first screen is built but off screen.

Troubleshooting and FAQ

Photos show a grey box with an image icon

The asset did not load. If you copied the source into your app, set BlogPackage.name to null and declare assets/images/ in your pubspec.yaml. If you use the package, check the path in the JSON matches a file (assets/images/<name>, case-sensitive) and restart the app: new assets need a full restart, not a hot reload.

"No BlogScope above this context"

A view was built outside BlogApp. Screens resolve their view models from the container that BlogApp creates; if you build views yourself (for example with go_router), wrap them in BlogScope and BlogProviders as shown in the router section.

Toasts do not appear

CairnToast.show finds the nearest CairnToaster. BlogApp includes one. If you assemble the shell yourself, put a CairnToaster above it.

The home page shows "We could not load the posts"

Your data source threw, or the mapper rejected the JSON (unknown author id, missing title, an unknown block type). Run the mapper in a test against your JSON, or print the error in your data source; the exception names the field.

A new category or post does not show

Posts are loaded once per mounted BlogApp. Hot reload does not re-run the seed's loading; use hot restart. With a real backend, call PostsFeedCubit.load() to refresh.

Fonts look different from the screenshots

The screenshots use Geist, the typeface Cairn's own tests use. Without a fontFamily on your CairnTheme text uses the platform's default.

Text overflows in my widget tests but not on a device

Placeholder test fonts. See the testing section: register a font and set it on the theme.

Search on a phone: where is the box?

Under 640 logical pixels the field folds behind the magnifier icon in the navbar and opens in a row under it. It stays open while there is a query.

Can I have more than one category per post?

Not out of the box: Post.category is a single string. Use tags for the rest, or change the model, PostMapper and QueryPosts.

Can the article body use Markdown or HTML?

The renderer draws blocks, not markup. Convert in your data source or mapper. That keeps the widgets small and the rendering consistent in light and dark.

Does it run on mobile and desktop?

Yes. Nothing is web-specific; the layout follows the width it is given.

Migration notes

Upgrading cairn_ui

  1. Read the cairn_ui changelog for the new version, looking at the components listed under "Cairn components used".
  2. Bump the constraint (cairn_ui: ^0.3.0, for example) and run flutter pub upgrade cairn_ui.
  3. Run flutter analyze. Renamed constructors and parameters show up as compile errors in the files below.
  4. Run flutter test. The widget tests catch layout regressions at the three widths. Look at the app in light and dark.

Upgrading the template itself

  • As a path or git package: update and run the tests. Public API is BlogApp, the three data source interfaces, BlogBrand, BlogConfig and BlogPackage. Anything else is internal and may change in a minor release.
  • As copied source: diff lib/ against the new version. The files you will have edited are blog_seed.dart (replace or delete), blog_brand.dart, blog_config.dart, blog_package.dart and blog_injection.dart; merge the rest.
  • Breaking for you means: a change to the JSON contract (a new required field), the interfaces of the data sources, or the constructor of BlogApp. These are called out in the release notes and will bump the major version.
